# LTE / IMS 验证例程仓库完整说明书

> 版本：2026-09-18  
> 适用对象：第一次拿到仓库的同事、测试人员、复核人和后续协议栈开发者。  
> 本文是仓库使用、目录文件、一键运行、证据查看和结果解释的统一权威版本。  
> 本文取代旧版 `docs/98-仓库目录与文件说明-20260917.md`、`docs/100-同事完整交接说明书-20260918.md`、`docs/101-同事使用与离线环境说明书-20260918.md`。

## 1. 先看结论边界

本仓库是一套“官方 TP 对齐的验证例程基线”，不是已经取得官方一致性证书的测试报告。

| 能做什么 | 不能证明什么 |
|---|---|
| 复现固定 commit 内的标准映射、套件文档、checker 和历史证据 | 不能证明自研协议栈已经通过 36.523-1 或 34.229-1 一致性 |
| 用真实日志或测试床输出执行 L1 字段和行为检查 | 不能替代合格 SS、仪表或认可实验室的官方 Verdict |
| 把官方 TP 的目的、步骤、消息判据和证据边界固定下来 | 不能证明第三方入网或运营商准入已经通过 |
| 为后续新协议栈提供一套可重复、可追溯的验收输入 | 不能把旧日志自动变成新代码的测试结果 |

必须记住：

- `UNIFIED RUNNER RESULT: OK` 只表示仓库基线可复现。
- `LOCAL_PASS`、`LIMITED_PASS`、`SELFCHECK_PASS` 都是本地或仓库级结果。
- `STANDARD_ALIGNED` 只表示已经按标准对齐，不表示执行通过。
- `OFFICIAL_PASS` 和 `OFFICIAL_FAIL` 只能来自合格 SS、仪表或认可实验室。
- 缺少 eNB、EPC、IMS、媒体、抓包或仪表时，必须保留 `RESTRICTED`、`NOT_EXECUTED` 或 `L2_REQUIRED`，不能伪造 PASS。

## 2. 术语说明

| 术语 | 在本仓库中的含义 |
|---|---|
| TC | 本仓库内部稳定编号 `TC-001` 到 `TC-034`，用作功能例程索引。 |
| 官方 TP | 官方测试过程或测试用途骨架，包括前置条件、过程、Expected Sequence、消息内容和 Verdict 判据。 |
| Annex | 3GPP/ETSI 正文后的附录。官方消息表、测试配置或补充过程可能放在 Annex 中，不能只看正文主章节。 |
| SS | System Simulator，系统模拟器。合格 SS 能模拟网络侧并按官方 TP 判定 UE 的 P/F。 |
| PIXIT | 测试实现参数。不同算法、定时器或网络配置可能要求分轮执行，例如 IPsec 算法轮次。 |
| L0 | 静态标准对齐、套件完整性、元数据和脚本自检层。 |
| L1 | 本地真实日志、模拟器、测试床或单元测试层，只能产生实现证据。 |
| L2 | 合格 SS、仪表或实验室按官方 TP 执行并产生官方 Verdict 的层。 |
| fresh-DUT | 针对新编译协议栈重新产生的证据，不能复用历史黄金日志冒充新结果。 |
| Golden replay | 对固定 commit 中的历史证据重新跑 checker，用于证明仓库快照可复现。 |

## 3. 最短交接路径

### 3.1 Windows

```powershell
git clone https://github.com/xiongqian-a/lte-verification.git
cd lte-verification
git checkout <full-commit-hash>
.\bootstrap.cmd --doctor
.\bootstrap.cmd --verify-standards
.\bootstrap.cmd
python -X utf8 runners\verify_portable_install.py --full
```

### 3.2 Linux 或 macOS

```sh
git clone https://github.com/xiongqian-a/lte-verification.git
cd lte-verification
git checkout <full-commit-hash>
chmod +x bootstrap.sh
./bootstrap.sh --doctor
./bootstrap.sh --verify-standards
./bootstrap.sh
python3 -X utf8 runners/verify_portable_install.py --full
```

### 3.3 已经安装 Python 3.10+ 时

```sh
python -X utf8 run_official_suite.py
python -X utf8 runners/verify_standards_bundle.py
python -X utf8 runners/environment_doctor.py
```

### 3.4 交接验收至少看到

```text
STANDARDS BUNDLE: PASS
UNIFIED RUNNER RESULT: OK
PORTABLE INSTALL: PASS (FULL)
UNIFIED RUNNER: PASS FROM UNRELATED CWD
GENERATED ARTIFACTS: STABLE
OFFICIAL_VERDICT: null
```

只看到仓库 runner 为 `OK`，不能写成协议一致性 PASS。

## 4. 入口脚本的区别

| 文件 | 平台 | 作用 |
|---|---|---|
| `bootstrap.cmd` | Windows | 最简单的 Windows 入口，绕过 PowerShell 执行策略后调用 `bootstrap.ps1`。 |
| `bootstrap.ps1` | Windows | 查找 Python 3.10+，必要时通过 winget 安装 Python，然后执行统一 runner。支持 `--doctor`、`--verify-standards`、`--colleague-replay`。 |
| `bootstrap.sh` | Linux/macOS | 查找 Python 3.10+，必要时调用系统包管理器安装，然后执行统一 runner。 |
| `run.ps1` | Windows | 已经能直接运行 Python 时的轻量入口，不负责准备环境。 |
| `run_official_suite.py` | 全平台 | 核心统一 runner。重建库和报告，执行标准校验、套件检查、脚本自检、本地证据复跑和 L2 适配检查。 |
| `requirements.txt` | 全平台 | 声明核心 runner 只使用 Python 标准库，正常复跑不需要 `pip install`。 |

`run_official_suite.py` 当前按顺序执行：

1. 检查便携安装和机器路径约束。
2. 校验标准原文包的路径、字节数和 SHA256。
3. 从 registry 和套件文档重建机器可读库。
4. 重建 `verification-architecture.html`。
5. 校验套件元数据与 registry 一致性。
6. 重建详细进度表。
7. 检查 34 份套件文档必需章节。
8. 执行所有 checker 的正控和负控自检。
9. 复跑仓库内已经固化的本地证据。
10. 校验 TC-026 到 TC-031 的官方边界和 L2 证据 Schema。
11. 执行 L2 证据适配和语义保护检查。
12. 生成官方风格状态报告，但不生成官方 Verdict。

## 5. 数据流和验证链路

```text
3GPP / ETSI / RFC 原文
        |
        v
registry/official_tp_registry.json
        |
        v
suites/official_tp_suites/TC-xxx.md
        |
        v
registry/official_tp_library.json
        |
        +--> runners/tcxxx_*.py
        |         |
        |         v
        |    evidence/ 中的日志、抓包、单测或模拟器输出
        |         |
        |         v
        |    pass / fail / restricted / not executed
        |
        +--> generated/ 进度、自检、复跑矩阵和审计报告
        |
        +--> tools/build_verification_architecture.py
                  |
                  v
        verification-architecture.html

最终官方 P/F:
qualified SS / instrument / accredited laboratory
```

如果输入证据被替换、日志只有旧版本、或者没有实时 DUT，不能把“脚本跑通”归因给新协议栈。

## 10. 页面怎么用

直接用浏览器打开：

```text
verification-architecture.html
```

页面不依赖网络，也不需要启动服务器。

主要区域：

| 区域 | 用途 |
|---|---|
| 总览 | 显示 34 条 TC、映射数量、执行入口、受限数量和官方 Verdict 为 0。 |
| 模块架构 | 按 8 个模块查看功能范围。 |
| 用例库 | 搜索和筛选 TC，点击任意 TC 查看完整执行卡。 |
| 输入输出图谱 | 每条 TC 显示输入、官方过程、输出证据和判定边界。 |
| 服务器证据 | 按信号链查看日志、证据目录、证明范围和仓库副本。 |
| 证据正文 | 点击“查看证据正文”，显示行号、命中行、上下文、截断提示和原文件链接。 |
| 服务器路径 | 按系统角色解释目录职责、产出和边界。 |
| 执行流程 | 从官方正文到 L2 仪表裁定的阶段。 |
| 规范依据 | 各标准在套件中的职责和关联 TC。 |

### 10.1 证据正文查看器会做什么

- 只在 HTML 中嵌入有限的文本上下文，避免把大日志整份塞进页面。
- 标出与 TC、信号和证明点相关的命中行。
- 显示行号，并提示中间省略了多少行。
- 提供“打开原文件”链接，便于查看完整仓库副本。
- 对 pcap、压缩包、Office/PDF 和 0 字节文件只显示元数据和边界说明。
- 对只有服务器路径、没有仓库副本的材料，明确显示“当前 checkout 无副本”。

它不会：

- 把二进制抓包伪装成文本 PASS。
- 把路径存在等同于报文有效。
- 把本地日志自动升级为官方 Verdict。

先看：

```text
suites/official_tp_suites/TC-011-IMS初始注册.md
evidence/local/tc011-l1-20260916/
generated/92-验证例程详细进度总表-20260915.md
```

再执行：

```sh
python -X utf8 runners/tc011_register_flow.py
python -X utf8 runners/tc011_ipsec_ss_sim.py
```

要检查的证据：

- REGISTER Request-URI、From、To、Contact、Expires。
- 401 challenge 和第二次 REGISTER 的 Authorization。
- 200 OK 的注册结果。
- Security-Client 和 Security-Verify 是否出现。
- SUBSCRIBE 和 NOTIFY 是否出现。
- HMAC-MD5-96 和 HMAC-SHA-1-96 两轮 PIXIT 是否执行。
- transcript、verdict 和 summary JSON 是否一致。

截至当前基线，TC-011 的本地注册检查为 `LIMITED_PASS`，本地 IPsec/Security/SUBSCRIBE/NOTIFY 模拟为 `L1_LOCAL_SIMULATED`。它没有真实内核 `xfrm`、真实 DUT/SS、真实 eNB/EPC/IMS 和官方 SS Verdict，因此正式一致性仍为 `NO_OFFICIAL_VERDICT`。

## 12. Golden replay 与 fresh-DUT 的区别

这两个词描述的是两类完全不同的运行。

| 项目 | Golden replay | fresh-DUT |
|---|---|---|
| 输入 | 仓库中固定提交的历史日志、抓包、期望结果和摘要 | 当前代码刚产生的新日志、抓包、媒体流、计时结果 |
| 目的 | 证明这个仓库快照可以被另一台机器复现 | 证明修改后的协议栈在当前测试环境下出现了什么行为 |
| 结果 | `LOCAL_PASS`、`LIMITED_PASS`、`SELFCHECK_PASS` 等 | 新的 `LOCAL_PASS` 或失败证据；仍不等于官方 Verdict |
| 是否能验证新代码 | 不能。除非新代码重新生成输入，否则只是重复检查旧证据 | 可以产生实现级证据 |
| 是否改变官方结论 | 不能 | 只有在合格 SS 或实验室执行时，才可能有官方 P/F |

### 12.1 交接复跑应该使用 Golden replay

如果同事只是想确认“拿到的仓库和原提交一致”，执行：

```sh
python -X utf8 runners/colleague_replay_verification.py
```

或：

```powershell
.\bootstrap.cmd --colleague-replay
```

它检查固定 commit、标准包、历史证据和 TC-011 关键不变量。它不应该被描述成“新协议栈已经通过测试”。

### 12.2 验证改过的自研代码必须使用 fresh-DUT

如果同事修改了 UE、协议栈、IMS 客户端、媒体处理或定时器，应重新采集输入，至少记录：

1. 代码仓库和完整 commit hash。
2. 构建号、编译选项和运行二进制或镜像摘要。
3. 执行日期、执行人、服务器和网络拓扑。
4. UE、eNB/EPC、IMS、SS 或仪表版本。
5. 原始日志、抓包、媒体文件和 checker 输出。
6. 该次运行仍然缺失的环境和允许变体。

新证据应写入独立的 `outputs/` 或新的证据目录，不应覆盖 `evidence/` 中已经固定的历史黄金证据。历史证据可以用于回归和一个已知入口的对照，但不能当作新代码的运行结果。

### 12.3 判定新代码是否改善

先保持标准、前置条件和 checker 版本不变，只替换 DUT 输入。然后比较：

- 消息序列是否从失败步骤变成预期步骤。
- TP Verdict 所要求的字段、定时器、状态和允许变体是否增加或减少。
- 失败发生在哪一步，而不是只看最终脚本是否返回零。
- 修改是否引入新的负控失败、格式漂移或结果升级。

本地前后对比可以支持研发判断，但不能替代合格的 L2 执行。

## 13. 结果词与使用边界

| 结果词 | 含义 | 可以怎么写 | 不可以怎么写 |
|---|---|---|---|
| `LOCAL_PASS` | 本地输入满足当前 checker 判据 | 本地功能检查通过、已有实现证据 | 官方一致性通过、入网通过 |
| `LIMITED_PASS` | 核心行为通过，但仍有未覆盖变体、环境或字段 | 带限制的本地通过 | 无条件 PASS |
| `SELFCHECK_PASS` | checker 的正控和负控按预期工作 | 判定逻辑自检通过 | 产品协议栈通过 |
| `STANDARD_ALIGNED` | 官方过程、章节和判据已对齐 | 标准对齐完成，等待执行 | 已经执行通过 |
| `RESTRICTED` | 缺标准、网络、仪表、运营商数据或访问权限 | 环境受限，当前无法判定 | FAIL 或 PASS |
| `NOT_EXECUTED` | 没有对应的合格执行证据 | 尚未执行 | 默认通过 |
| `L2_REQUIRED` | 必须有合格 SS、仪表或实验室才能得到最终判定 | 需要 L2 执行 | 本地已经给出官方结论 |
| `OFFICIAL_PASS` / `OFFICIAL_FAIL` | 合格 SS 或认可实验室按官方 TP 产生的 Verdict | 官方一致性通过或失败 | 由本地脚本生成 |

负控 fixture 中的 `EXPECTED_FAIL` 只表示“这个故意错误的样例应当失败”，不是一条产品例程的正式结果。

报告时推荐使用下面的完整句式：

> TC-xxx 当前已完成官方 TP 对齐和本地字段或行为检查，结果为 `LOCAL_PASS` / `LIMITED_PASS`；由于缺少真实 eNB/EPC/IMS/SS 或仪表，正式官方 Verdict 仍为 `NO_OFFICIAL_VERDICT`。

## 14. 缺少环境时怎么继续

先运行环境诊断：

```sh
python -X utf8 runners/environment_doctor.py
```

或：

```powershell
.\bootstrap.cmd --doctor
```

诊断结果不改变仓库基线，只告诉你当前机器能做什么。

### 14.1 只缺第三方工具

如果只缺 `pjsua`、`ffmpeg`、`tshark`、Docker 或本地 IMS，不影响：

- standards bundle 校验；
- 34 份套件文档和 registry 校验；
- checker 自检；
- 固定历史证据复跑；
- 页面生成；
- 交接 Golden replay。

它影响的是新的实时端到端执行。此时应保留 `RESTRICTED` 或 `L2_REQUIRED`。

### 14.2 缺 eNB、EPC、IMS 或核心网

可以继续检查 L0 和已有 L1 证据；不能把本地单测、协议栈注入或开源模拟器的结果写成真实端到端结果。可以补做的工作包括：

1. 增加官方正文行锚和 `.3.2` 子步骤。
2. 增加离线 checker 正控和负控。
3. 在明确标注 `OPEN5GS`、`SRSRAN`、`OPENIMSCORE` 或 `PJSUA` 的独立环境生成新证据。
4. 把输入、拓扑、版本和限制一并保存。

开源或模拟环境输出仍然是 L1。

### 14.3 缺 SS、仪表或实验室

无法在仓库内补出官方 Verdict。应保留 `OFFICIAL_VERDICT: null`，准备好：

- 官方 TP 章节和子步骤。
- 每条消息、字段、定时器和允许变体。
- PIXIT 与测试配置。
- 证据 Schema 和适配器。
- 现场执行时需要填写的 DUT、SS、拓扑、日志和结果槽位。

一旦拿到合格 SS 或实验室结果，通过 L2 adapter 导入；不要覆盖本地证据，也不要手工把状态改成 `OFFICIAL_PASS`。

## 15. 路径、私有仓库和离线交接

### 15.1 路径

仓库入口、runner、标准包校验、报告生成和页面构建都从文件自身位置解析根目录。clone 到不同盘符、用户目录或 Linux 服务器后，不需要修改文件路径。

不要修改：

- `registry/`、`suites/`、`standards/official/manifest.json` 中的仓库相对路径；
- `runners/_paths.py` 或入口脚本的根目录计算逻辑；
- `generated/` 报告来绕过失败；
- 新同事不需要、原机器却有的盘符和用户目录。

### 15.2 私有仓库访问

最安全的做法是把同事的 GitHub 账号加入仓库 Collaborator，并只授予 `Read` 权限。

不要通过聊天发送：

- GitHub 密码；
- Personal Access Token；
- SSH 私钥；
- 服务器密码；
- 包含凭据的 `.env` 文件。

同事使用 HTTPS clone 时，应通过自己的 GitHub 凭据或组织的凭据管理器授权；使用 SSH 时使用自己的密钥。

### 15.3 离线传输

如果目标服务器无法访问 GitHub，可以由有权限的机器创建 Git bundle：

```sh
git bundle create lte-verification.bundle --all
```

在目标机器上：

```sh
git clone lte-verification.bundle lte-verification
cd lte-verification
git rev-parse HEAD
```

离线包仍然属于私有材料。标准原文、日志和抓包的转发范围必须符合公司和标准组织的授权。

### 15.4 Linux 服务器上运行

服务器至少需要：

- Git；
- Python 3.10+；
- 足够的磁盘空间保存标准包和证据；
- `bootstrap.sh` 可执行权限。

只有仓库基线不需要 eNB、EPC、IMS、Docker 或仪表。要在服务器上跑 fresh-DUT，服务器还必须具备对应网络功能、测试床、抓包和媒体工具。

## 16. 新增或修改一条 TC

内部 `TC-xxx` 编号是稳定索引，不要因为更换名称、阶段或负责人而重排编号。

推荐步骤：

1. 从 `suites/official_tp_suites/_templates/TC-TEMPLATE.md` 创建或更新套件文档。
2. 在 `registry/official_tp_registry.json` 中更新模块、官方规范、章节、映射等级、脚本、证据和 blocker。
3. 把官方正文位置写到行锚或 `.3.2`、`.3.3`、Annex 子步骤中。
4. 检查 Expected Sequence、Specific Message Contents、定时器、容差和允许变体。
5. 只有存在真实输入来源时，才增加或修改 checker。
6. 为 checker 同时准备正控和负控 fixture，防止空文件或错误报文被误判 PASS。
7. 在 suite、registry 和页面中写明证据层级和限制。
8. 重建库、页面和报告：

```sh
python -X utf8 runners/build_official_library.py
python -X utf8 tools/build_verification_architecture.py
python -X utf8 runners/gen_detailed_progress.py
```

9. 运行完整检查：

```sh
python -X utf8 run_official_suite.py
python -X utf8 runners/verify_portable_install.py --full
```

10. 检查 `git diff`，确认没有旧日志被误标为新 DUT、没有本地绝对路径、没有敏感值，也没有把 `RESTRICTED` 改成无条件 PASS。

## 17. 常见问题

### 17.1 为什么不是 34 条都有可执行判 PASS 的脚本？

34 是功能例程索引，不等于 34 份已经在合格 SS 上执行的官方一致性记录。只有已经拿到真实输入、正式正文骨架和有效 checker 的 TC 才能产出本地证据。其余条目应显式标成 `STANDARD_ALIGNED`、`RESTRICTED`、`NOT_EXECUTED` 或 `L2_REQUIRED`。

### 17.2 为什么页面里有些日志只能看说明？

有三种正常情况：

- 文件是 pcap、Office、PDF、压缩包或二进制，页面只展示元数据，不伪造文本；
- 证据只在服务器，仓库没有获得授权副本；
- 日志没有当前 TC 的关键信号，或文件为 0 字节。

这些情况都必须保留原始边界，不能因为页面不能预览就直接判 PASS。

### 17.3 一键运行会安装 eNB、EPC、IMS 或仪表吗？

不会。bootstrap 只能准备 Python 和运行仓库基线。它不会安装、模拟或伪造核心网、IMS、SS 和仪表。缺实时环境的条目会继续受限。

### 17.4 为什么同事拿到仓库会看到和原作者相同的 Golden replay 结果？

因为 checker 读取的是固定 commit 内的同一组历史证据和 registry。它证明交接快照一致，不证明同事机器上重新建立了一个真实核心网。

### 17.5 同事修改代码后还能直接复用原来的 PASS 吗？

不能。原来的 PASS 针对旧输入和旧代码。修改后必须重新采集 fresh-DUT 证据，再用同一标准骨架检查。

### 17.6 看到 `UNIFIED RUNNER RESULT: OK` 是否代表验收完成？

它代表仓库基线完整且可复现。交接验收还要同时检查标准包、便携性、生成产物稳定性和 `OFFICIAL_VERDICT: null`。协议一致性和第三方入网仍未完成。

### 17.7 如何判断页面上的一条证据是不是有效？

至少检查：

1. 该证据关联哪个 TC。
2. 输入来自什么设备、测试床或历史快照。
3. 命中的具体消息、字段和行号。
4. 是否有相应用例的官方骨架。
5. 结论是本地证据、受限还是官方 Verdict。
6. 是否使用了当前 DUT 代码，而不是旧日志。

## 18. 交接验收清单

交接时应记录并确认：

1. 完整 commit hash，而不是只写 `main`。
2. `git status --short --branch` 的结果。
3. `python -X utf8 runners/verify_standards_bundle.py` 输出 `STANDARDS BUNDLE: PASS`。
4. `python -X utf8 runners/environment_doctor.py` 对 golden replay 和 fresh-DUT 的结论。
5. `python -X utf8 run_official_suite.py` 输出 `UNIFIED RUNNER RESULT: OK`。
6. `python -X utf8 runners/verify_portable_install.py --full` 输出 `PORTABLE INSTALL: PASS (FULL)`、`UNIFIED RUNNER: PASS FROM UNRELATED CWD` 和 `GENERATED ARTIFACTS: STABLE`。
7. `git status --short` 在确定性生成后仍保持预期状态。
8. `verification-architecture.html` 能在离线状态打开，34 条输入输出图谱存在，证据正文和缺口说明可打开。
9. 报告中仍有 `OFFICIAL_VERDICT: null`，没有被误写成一致性 PASS。
10. 同事知道哪些结果是 Golden replay，哪些必须用自己的 fresh-DUT 重新采集。

## 19. 推荐阅读顺序

第一次接手时建议按以下顺序：

1. 本说明书第 1、3、4 节：范围和最短路径。
2. `README.md`：仓库总览和结果词。
3. `START-HERE.md`：最短操作入口。
4. `verification-architecture.html`：建立模块、TC、官方映射、输入输出和证据视图。
5. 目标 TC 的 `suites/official_tp_suites/TC-xxx-*.md`：逐条执行卡和标准骨架。
6. `registry/official_tp_registry.json`：机器可读映射。
7. `runners/run_tc_evidence.py` 和对应 `tcxxx_*.py`：实际 checker。
8. `evidence/` 和 `generated/`：输入证据及复跑结果。
9. `docs/102-*`、`docs/103-*` 和 `docs/102a-*`：需要追踪服务器原始材料时再查。

任何显示“通过”的本地结果，都必须同时附带它的层级、输入来源、官方骨架和未覆盖边界。
