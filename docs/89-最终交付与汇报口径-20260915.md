## 3. 证据与结论分级

| 结论 | 含义 | 当前使用范围 |
|---|---|---|
| `LOCAL_PASS` | 本地日志、报文或代码行为符合脚本断言的字段/行为判据 | 只能作为研发行为证据 |
| `LIMITED_PASS` | 核心本地行为通过，但标准要求仍有变体、字段或环境未覆盖 | 必须保留受限说明 |
| `SELFCHECK_PASS` | 判定脚本可执行，合成夹具正负控行为符合预期 | 不是产品一致性 |
| `STANDARD_ALIGNED` | 官方 TP、章节、消息和判据已建立骨架，但本地未执行完整流程 | 准备进入 L2 |
| `RESTRICTED` | 缺外部规范、网络、仪表或运营商输入，当前不能判 | 不是 FAIL，也不是 PASS |
| `OFFICIAL_PASS / FAIL` | 合格 SS 或检测机构按官方 TP 给出 Verdict | 当前环境不可产生 |

### 3.1 汇报时必须保留的限定语

## 7. 后续自研协议栈如何使用这套基线

后续自研协议栈不应修改 TC 编号来掩盖差异。正确做法是：

1. 保留本套 `TC-001~034` 作为内部功能追溯编号。
2. 每条实现变更必须继续关联 `official_tp_registry.json` 中的官方规范、章节和正文行号。
3. 每轮提交先跑 `run_official_suite.py`，确保套件、注册表、用例库和本地证据没有回归。
4. 新增行为只能通过新增证据或升级 L2 manifest 来提升结论，不能手改 `LOCAL_PASS` 为 `OFFICIAL_PASS`。
5. 自研栈完成后，先跑本套 L0/L1 证据，再将同一批用例送入合格 SS/检测机构执行 L2。
6. 送审时以官方 TC 编号和 TP Verdict 为骨架，内部 TC 编号只作追溯，不作为实验室判例编号。
