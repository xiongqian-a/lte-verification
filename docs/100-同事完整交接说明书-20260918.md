# 同事完整交接说明书

> 适用对象：第一次拿到本仓库、需要接手标准例程或复核结果的同事。
>
> 目标：不修改项目路径，不改脚本里的机器名，不依赖原会话记忆，运行仓库内
> 已有的验证基线，并正确解释结果。
>
> 关键边界：本仓库保存的是“官方 TP 骨架 + 可执行本地方案 + 历史/模拟证据”，
> 不是 36.523-1、34.229-1 或第三方入网的官方一致性执行记录。

## 1. 一分钟结论

同事拿到仓库后分三种任务：

| 任务 | 一条命令 | 需要什么 | 能得到什么 |
|---|---|---|---|
| 检查标准原文包 | `.\bootstrap.cmd --verify-standards` | Git、Python 3.10+ | 45 份原文的路径、大小、SHA256 校验结果 |
| 检查本机环境 | `.\bootstrap.cmd --doctor` | Git、Python 3.10+ | 哪些能力可跑，哪些端到端环境缺失 |
| 复现当前黄金结果 | `.\bootstrap.cmd --colleague-replay` | Git、Python 3.10+ | 固定 commit、历史证据复跑、TC-011 不变量、`OFFICIAL_VERDICT: null` |
| 验证同事修改后的新代码 | 需要 fresh-DUT 测试台 | 新代码、eNB/EPC/IMS、媒体、抓包或合格 SS | 新的 `FRESH_DUT` 日志；仍不等于官方 Verdict |

如果只做交接验收，重点看：

```text
STANDARDS BUNDLE: PASS
COLLEAGUE REPLAY: PASS
TC011_INVARIANTS: PASS
OFFICIAL_VERDICT: null
```

如果缺少 IMS、EPC、eNB、pjsua、ffmpeg、tshark 或一致性仪表，不要修改日志和
结论来“凑 PASS”。先运行 `--doctor`，把缺口如实保留为 `RESTRICTED`、
`NOT_EXECUTED` 或 `L2_REQUIRED`。

## 2. 这个仓库到底在验证什么

“验证例程”不是一个单独的脚本，也不是一份单独的 Markdown。它由四层组成：

1. **标准来源层**：3GPP/ETSI 原文、版本、章节和行锚。
2. **官方 TP 用例层**：`suites/official_tp_suites/` 中 34 条 TC 的目的、
   前置、步骤、Expected Sequence、TP Verdict 和消息内容。
3. **执行层**：`runners/` 中读取日志、抓包或测试台输出并做字段/行为判断的
   脚本。
4. **证据层**：`evidence/` 中固定下来的日志、抓包、模拟器输出和摘要。

最后再生成：

- `generated/`：统一 runner 重建的复跑矩阵、自检状态、详细进度和报告；
- `outputs/colleague-replay/`：同事本次复跑生成的 Markdown/JSON 验收报告。

因此 `LOCAL_PASS` 只能说明“输入日志符合当前 checker 的判据”。它不能自动变成
官方一致性 PASS。

## 3. 三层环境与结果口径

| 层级 | 环境 | 例子 | 结果词 |
|---|---|---|---|
| L0 | Git + Python，仓库原文和映射 | 检查 TC、标准条款、脚本自检 | `STANDARD_ALIGNED`、`SELFCHECK_PASS` |
| L1 | 本地测试台或模拟器 | pjsua、Open5GS、srsRAN、本地 IMS、抓包 | `LOCAL_PASS`、`LIMITED_PASS`、`RESTRICTED` |
| L2 | 合格 SS、仪表或检测机构 | R&S、Anritsu、Keysight、认证实验室 | `OFFICIAL_PASS`、`OFFICIAL_FAIL` |

当前仓库已经能让同事复现 L0/L1 的历史基线。它不会自动启动 L1 核心网，也不会
提供 L2 仪表。

## 4. 获取仓库

### 4.1 在线 clone

```powershell
git clone https://github.com/xiongqian-a/lte-verification.git
cd lte-verification
```

私有仓库使用 HTTPS 时需要 GitHub 凭据；使用 SSH 时需要有仓库读取权限的密钥。

### 4.2 固定 commit 复跑

交接验收必须使用 full commit hash，不能只写“main 最新”。

```powershell
git fetch origin
git checkout <full-commit-hash>
git rev-parse HEAD
git status --short --branch
git remote -v
```

### 4.3 离线交接

如果服务器不能直接访问 GitHub，优先使用 Git bundle，而不是只复制工作目录：

```powershell
git bundle create lte-verification.bundle --all
git bundle verify lte-verification.bundle
```

同事侧：

```powershell
git clone lte-verification.bundle lte-verification
cd lte-verification
git remote -v
git rev-parse HEAD
```

也可以把整个仓库目录压缩后传输。压缩包必须包含 `.git`、`standards/` 和
`evidence/`；只复制源码目录会丢失固定提交和黄金证据。

### 4.4 为什么不需要修改项目路径

入口和 runner 都从自己的文件位置解析仓库根目录，不依赖原机器的绝对路径。核心
方式是：

```python
ROOT = Path(__file__).resolve().parent.parent
```

例如 `runners/verify_standards_bundle.py` 无论位于：

```text
C:\handoff\lte-verification\runners\verify_standards_bundle.py
D:\team\repos\lte-verification\runners\verify_standards_bundle.py
/home/user/repos/lte-verification/runners/verify_standards_bundle.py
```

都会把上一级目录识别为仓库根目录。`run_official_suite.py` 也会以仓库根目录为
工作目录调用各步骤。因此：

1. 不要修改 TC、registry、manifest 或 runner 中的路径。
2. 不要创建与原机器相同的盘符或目录名。
3. 不需要在系统环境变量里配置仓库路径。
4. clone 后应从仓库根目录执行 `bootstrap`；如果从其他目录调用，应使用脚本的
   完整路径。

如果运行脚本后出现大量“找不到文件”，优先检查是否漏传了 `standards/`、
`suites/`、`registry/` 或 `evidence/`，不要把相对路径改成同事机器上的绝对路径。

## 5. 第一次运行

### 5.1 Windows

```powershell
.\bootstrap.cmd --doctor
.\bootstrap.cmd --verify-standards
.\bootstrap.cmd --colleague-replay
```

### 5.2 Linux/macOS

```sh
chmod +x bootstrap.sh
./bootstrap.sh --doctor
./bootstrap.sh --verify-standards
./bootstrap.sh --colleague-replay
```

### 5.3 已安装 Python 3.10+ 时直接运行

```text
python -X utf8 runners/environment_doctor.py
python -X utf8 runners/verify_standards_bundle.py
python -X utf8 run_official_suite.py
python -X utf8 runners/colleague_replay_verification.py --expected-commit <hash>
```

脚本从自身位置计算仓库根目录，因此仓库放在 `D:\handoff`、
`/home/user/lte-verification` 或其他任意目录都可以。不要手工修改脚本中的
路径。

### 5.4 交接复跑和新 DUT 验证不是同一件事

同事需要先选择任务：

| 任务 | 输入 | 输出 | 是否使用仓库旧日志 |
|---|---|---|---|
| 交接/复核现有基线 | 固定 commit + 仓库内容 | `COLLEAGUE REPLAY` 报告，证明仓库、标准包、套件和旧证据可复现 | 是，这是有意复跑的黄金证据 |
| 验证同事修改后的协议栈 | 新 DUT commit、编译产物、实时 eNB/EPC/IMS 或本地测试床、新抓包/日志 | `FRESH_DUT` 证据，只能作 L1 实现证据 | 否，禁止使用旧日志代替新结果 |
| 正式一致性 | 合格 SS、仪表或检测机构 | 官方 TP Verdict | 不使用本仓库的历史 PASS 代替 |

交接复跑可以把仓库中的日志作为输入，因为它验证的是“这份固定快照能否复现”。
验证新代码时必须重新生成日志；如果报告只有旧日志，就不能把结果归因给新代码。

## 6. `--doctor` 怎么读

`--doctor` 不会自动安装 IMS、EPC、eNB、pjsua 或仪表。它只检查本机可见性，
并输出：

```text
GOLDEN_REPLAY_READY: YES
CHECKER_ONLY_READY: YES
FRESH_DUT_ENV_READY: NO
FRESH_DUT_ENV_MISSING: network_core, radio, ims_sip
OFFICIAL_SS_REQUIRED: YES
OFFICIAL_SS_DETECTED: NO
```

含义如下：

| 输出 | 含义 |
|---|---|
| `GOLDEN_REPLAY_READY: YES` | 可以复跑仓库内已提交的证据，不需要实时核心网。 |
| `CHECKER_ONLY_READY: YES` | 可以运行 checker 自检和标准映射检查。 |
| `FRESH_DUT_ENV_READY: NO` | 缺少至少一类实时测试依赖，不能声称已经重新跑端到端。 |
| `FRESH_DUT_ENV_MISSING` | 缺哪些工具组；具体组名会明确列出。 |
| `OFFICIAL_SS_REQUIRED: YES` | 官方 Verdict 必须由合格 SS/实验室产生。 |
| `OFFICIAL_SS_DETECTED: NO` | 本脚本不能自动判定仪表是否合格，必须外部确认。 |

`FRESH_DUT_ENV_READY` 是保守值。某些单独 TC 可能只需要其中一个子集，但仓库
不会因为某一个进程存在就自动把整套端到端环境判为 ready。

## 7. 标准原文包怎么用

### 7.1 目录

```text
standards/
├── README.md
└── official/
    ├── manifest.json
    ├── 24.173/
    ├── 24.229/
    ├── ...
    └── 36.523-2/
```

### 7.2 校验

```text
python -X utf8 runners/verify_standards_bundle.py
```

成功：

```text
STANDARDS BUNDLE: PASS
FILES: 45
TOTAL BYTES: 144416074
```

`manifest.json` 中每个文件都记录：

- 规范名和版本；
- 仓库相对路径；
- 文件格式和字节数；
- SHA256。

失败时不要忽略。先确认是否漏传文件、Git LFS 指针没有展开、复制过程中截断，
或者文件被替换成其他版本。校验失败的报告不能作为原文复核完成。

### 7.3 版本选择

当前包保留多个版本是有意的：

- `36.523-1 V14.3.0` 是 LTE/EPC 官方 TP 主骨架。
- `34.229-1 V14.7.0` 是当前 IMS TP 行锚主版本；`V14.8.0` 用于版本差异，
  不能直接替换所有 V14.7.0 行锚。
- `36.508 V14.3.0` 是当前主要测试环境配置版本；`V18.6.0` 仅作后续差异参考。
- `34.108 V14.2.0` 和 `V11.14.0` 都保留，因为不同 TC 的历史锚点版本不同。

人工核对时先看 TC 文档写的是哪个版本，再看 `standards/README.md` 和
`manifest.json`，不要跨版本猜行号。

### 7.4 当前没有纳入的依赖

标准包不是“3GPP 全部规范”。当前 45 份文件已经覆盖仓库现有 `suites/` 和
`registry/` 直接引用的 3GPP/ETSI TS，以及 `RFC 3261`、`RFC 3515`。仍缺：

- 具体 YD/T 编号和运营商 VoLTE 入库企标；
- 后续新增 TC 才会引入的其他 3GPP 规范原文。

这些缺口会影响相应 TC 的完整标准核对。相关结论继续标 `RESTRICTED`、
`PARTIAL` 或 `NOT_EXECUTED`，不能凭空补成 PASS。

## 8. 黄金证据复跑：看什么才算通过

执行：

```powershell
.\bootstrap.cmd --colleague-replay
```

通过时必须看到：

```text
COLLEAGUE REPLAY: PASS
COMMIT_MATCH: True
TC011_INVARIANTS: PASS
OFFICIAL_VERDICT: null
```

报告位置：

```text
outputs/colleague-replay/
```

这次 PASS 证明：

- 仓库是同一个固定 commit；
- 统一 runner、标准包、34 条套件元数据和 checker 自检可运行；
- 已提交的本地证据能按原判据复跑；
- TC-011 仍保持 `LIMITED_PASS / L1_LOCAL_SIMULATED`，没有伪造官方判定。

这次 PASS 不证明：

- 重新连接过真实 eNB、EPC、IMS、HSS 或 SS；
- 重新生成过新的现场日志；
- 拿到了官方 36.523-1、34.229-1 或第三方入网 Verdict。

### 8.1 黄金证据与旧日志的隔离

`evidence/` 中的日志是交接基线，不是同事新代码的结果。同事修改自研协议栈后，
不能让 checker 继续读这些旧日志并写一个 PASS，否则结果没有验证价值。

新代码验证必须满足：

1. 记录 DUT 源码 commit；
2. 记录编译产物和 SHA256；
3. 从他的构建新产生 SIP/SDP/RTP/媒体日志；
4. 新日志写入独立目录，例如 `outputs/fresh-dut-<date>/`；
5. 报告写明 `EVIDENCE_SOURCE: FRESH_DUT`；
6. 不复用 `evidence/` 中的旧日志；
7. 本地 PASS 仍不能升级为官方一致性 PASS。

## 9. 单条 TC 怎么跑

打开：

```text
suites/official_tp_suites/TC-xxx-*.md
```

按以下顺序阅读和执行：

1. 用例 ID、目的、来源规范和版本；
2. 前置条件和 SS 环境；
3. `.3.1` / `.3.2` / `.3.3` 官方步骤和 Expected Sequence；
4. 消息字段、容差、允许变体和 TP Verdict；
5. 本地执行命令；
6. 原始证据路径；
7. 当前 `RESTRICTED` / `LIMITED_PASS` / `L2_REQUIRED` 边界。

### 9.1 TC-011 手工演示

查看用例文档：

```text
python -X utf8 -c "from pathlib import Path; print(Path('suites/official_tp_suites/TC-011-IMS初始注册.md').read_text(encoding='utf-8'))"
```

运行 REGISTER 基础自检：

```text
python -X utf8 runners/tc011_register_flow.py --selfcheck
```

复跑仓库内基础注册证据：

```text
python -X utf8 runners/tc011_register_flow.py --log evidence/external/tc12-tc13-calls-raw.log
```

运行 IPsec/SUBSCRIBE/NOTIFY 本地 L1 自检：

```text
python -X utf8 runners/tc011_ipsec_ss_sim.py --selftest --out-dir evidence/local/tc011-l1-20260916
```

演示时不要只看最后一行的 PASS，要同时打开：

- `suites/official_tp_suites/TC-011-IMS初始注册.md`；
- `suites/official_tp_suites/_substeps/TC-011-015-032-official-tp-blocks.md`；
- `suites/official_tp_suites/_substeps/TC-011-014-annexA-message-contents.md`；
- 对应原始 pjsua 日志或本地 transcript；
- `runners/tc011_register_flow.py` 和 `runners/tc011_ipsec_ss_sim.py`。

TC-011 当前仍是本地/模拟 L1 证据，不是真实 SA、真实 DUT/SS 或官方 Verdict。

## 10. 没有核心网、IMS 或仪表时怎么办

### 10.1 没有 Python

Windows 运行 `bootstrap.cmd`，脚本会尝试通过 `winget` 安装 Python 3.12；
Linux/macOS 运行 `bootstrap.sh`，脚本会尝试系统包管理器。公司服务器不允许安装
软件时，使用已有 Python 3.10+，或让管理员从发行版仓库安装。

### 10.2 没有 Git

可以下载仓库压缩包，但无法可靠检查 full commit，也无法运行要求 Git 的复跑
报告。最稳妥的方式是在服务器安装 Git，或者使用 Git bundle 在另一台有 Git 的
机器导出固定提交。

### 10.3 没有 Docker、Open5GS、srsRAN 或 pjsua

仍然可以：

- 校验标准原文包；
- 检查 TC、官方章节、步骤和映射；
- 运行 checker 自检；
- 复跑仓库中已经提交的黄金证据。

不能：

- 声称完成了一次新的 eNB/EPC/IMS 端到端执行；
- 用旧日志代替新 DUT 日志；
- 把本地模拟升级成官方一致性。

不同缺口的处理方式：

| 缺口 | 只做交接复跑 | 要做 fresh-DUT/L1 |
|---|---|---|
| Docker | 不需要 | 可用官方容器或实验室提供的镜像，必须先确认镜像版本和网络配置。 |
| Open5GS/EPC | 不需要 | 必须有可用 EPC、PLMN、APN/DNN、SIM 和承载配置。 |
| srsRAN/eNB | 不需要 | 必须有可用射频或等效无线测试环境，并确认频点、带宽和 UE 接入参数。 |
| pjsua/Asterisk/FreeSWITCH | 不需要 | 可用于 IMS/SIP 功能级测试，但不能替代合格 IMS SS。 |
| tshark/Wireshark | 不需要 | 用于抓包和字段核对；原始 pcap 必须随新证据保存。 |
| ffmpeg/媒体工具 | 不需要 | 用于检查 RTP、编解码、DTX/SID 或媒体流；没有媒体原始数据时不能判媒体行为。 |

仓库不会自动下载这些系统。Linux 服务器可以由管理员按发行版安装基础工具，但
Open5GS、srsRAN、IMS 和仪器侧配置必须使用对应版本的官方安装文档或测试床配置，
不能靠猜测命令强行拼出一个“看起来能跑”的环境。

### 10.4 没有仪表或检测机构

本仓库不能补出官方 Verdict。继续保留：

```text
OFFICIAL_VERDICT: null
```

若有合格 SS，按其远程接口、日志导出和 evidence manifest 流程接入 L2。没有
Verdict 文件时，适配器必须保持 `NOT_EXECUTED` 或 `RESTRICTED`。

### 10.5 服务器环境不一致

先收集：

```powershell
git rev-parse HEAD
git status --short --branch
python --version
python -X utf8 runners/environment_doctor.py --json
```

Linux 再记录：

```sh
uname -a
cat /etc/os-release
```

不要通过修改生成报告来掩盖差异。先确定差异来自哪一层：

- 标准包哈希不同：恢复原文包；
- runner 结果不同：比较 commit、Python 版本、文件 hash 和完整日志；
- fresh-DUT 结果不同：比较 DUT commit、二进制 hash、网络配置和抓包；
- 官方 Verdict 不同：只能以合格 SS/实验室输出的证据为准。

### 10.6 服务器不能安装任何软件时，最少还能做什么

只要服务器有下载/读取仓库的能力，并有一台能运行 Git 和 Python 3.10+ 的机器，
就可以完成最小交接验收：

```text
git clone <仓库地址>
cd <clone 目录>
.\bootstrap.cmd --verify-standards
.\bootstrap.cmd --colleague-replay
python -X utf8 runners/verify_portable_install.py --full
```

Linux/macOS 把前两条换成 `./bootstrap.sh --verify-standards` 和
`./bootstrap.sh --colleague-replay`。

必须看到：

```text
STANDARDS BUNDLE: PASS
COLLEAGUE REPLAY: PASS
TC011_INVARIANTS: PASS
OFFICIAL_VERDICT: null
PORTABLE INSTALL: PASS (FULL)
```

如果服务器既不能安装 Git/Python，也不能运行这些命令，那么它只能做文件级查看，
不能产生可追溯的交接复跑结论。此时应让管理员提供 Python 3.10+ 和 Git，或者把
仓库带到一台具备基础工具的机器上执行；不要用人工改写报告的方式绕过。

## 12. 常见问题

### 12.1 “为什么仓库有标准原文，运行时还会说缺标准？”

“缺标准”通常指没有对应版本的直接原文，或某个 TC 还缺 33.x、RFC、YD/T 等
依赖。仓库标准包存在不等于所有外部依赖已经齐全。

### 12.2 “为什么不能直接用 OpenIMSCore/FreeSWITCH 替官方 IMS SS？”

它们可以产生 L1 功能证据，但没有官方 TP Verdict，不能替代合格 SS 或实验室。

### 12.3 “为什么黄金证据 PASS 但不能判定我修改后的代码？”

黄金证据是历史输入。要验证新代码，必须重新构建 DUT、重新生成日志，并在新目录
中运行 checker。旧日志只能证明旧输入可复现。

### 12.4 “为什么标准哈希校验失败后不能继续？”

说明 checkout 不是同一份原文快照。继续核对会产生不可追溯的版本差异，应先恢复
正确文件。

### 12.5 “是不是必须安装所有服务器软件才能接手？”

不是。只做交接复现、标准核对和已有证据复核时，不需要 IMS/EPC/eNB。只有要
重新跑实时端到端或目标 DUT 新日志时，才需要相应测试台。
