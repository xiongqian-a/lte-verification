# 下午汇报稿（模块与案例版）

> 建议时长：10 到 12 分钟。
>
> 汇报主线：整体模块 -> 官方对齐方法 -> 两个实际案例 -> 结果、限制与边界。
>
> 核心口径：当前成果是“官方 TP 对齐的可执行验收基线”，不是官方一致性执行记录。本地 PASS 不等于 36.523-1 / 34.229-1 一致性，也不等于第三方入网通过。

## 一、开场

今天我不逐条展开 34 个用例，主要讲四件事：

1. 我们的验收套件覆盖哪些模块，每个模块解决什么问题。
2. 这些用例是怎么和 3GPP 官方规范、官方 TP 和具体条款对齐的。
3. 用两个实际案例说明我们已经做到什么，以及还差什么。
4. 当前结果能不能作为自研协议栈的验收基线，边界在哪里。

开场可以直接说：

> 这次工作的目标，是给后续自研协议栈提前定下一套可追溯、可复跑的验收尺子。重点不是在没有仪表的情况下宣称官方一致性已经通过，而是把标准、测试流程、判据、证据和正式送审之间的路径先搭起来。

## 三、怎么对齐官方协议

这里建议重点讲，因为这是和普通“自研功能测试”最大的区别。

### 3.1 第一步：找到正确的官方规范和版本

我们不是只凭协议知识写条款号，而是先确定每类用例的正式来源：

- EPS、承载、跨制式、SSAC、紧急业务：`36.523-1`，并关联 `36.508`、`36.509`、`34.108`、`36.523-2`。
- IMS 注册、SIP 呼叫、保持、会议、媒体基础流程：`34.229-1`。
- SIP 协议行为和定时器：`24.229`。
- ESM、PDN REJECT、T3482、cause #32：`24.301`。
- 补充业务和 REFER：`24.628`、`24.173`。
- MTSI、SDP、媒体和 QoS：`26.114`。
- VAD/DTX 和静默帧：`26.093`、`26.193`、`26.450`、`26.451`。

同时明确版本。例如 Release 14 的 IMS 正文主锚使用 `34.229-1 V14.7.0`。后来提供的 `V14.8.0` 已经将测试要求指向 Release 15，并把 `5 to 22` 和 Annex A 到 J 标为 Void，不能拿它强行重锚 Release 14 的行号。

可以概括为：

> 第一步不是写测试步骤，而是先确认“这条用例到底应该归哪份规范、哪个版本、哪个正式章节”。版本不对，后面的判据就没有意义。

### 3.2 第二步：按照官方 TP 结构拆用例

官方案例通常会明确这些内容：

- Pre-test conditions：测试前环境和 UE 状态。
- Test procedure：SS 和 UE 的动作。
- Expected sequence / Main behaviour：期望的消息序列。
- Specific message contents：具体消息字段和允许条件。
- TP Verdict：官方判定点和 P/F 结论。

我们把这些内容转成内部可执行套件，同时保留：

- 官方规范名称和版本；
- 官方章节号或官方 TC 编号；
- 正文行号锚点；
- 相关 Annex 和前置规范；
- 每条断言的来源；
- 当前证据层级和受限原因。

目前结果是：

- 34 条标准套件文档齐备；
- 32 条已有官方正文行号锚；
- 28 条达到 `exact_line_ref`；
- 其余按 `partial`、`behavior` 或外部依赖如实标注。

可以概括为：

> 我们保留内部 TC 编号方便研发追溯，但正式测试判据尽量以官方 TC、官方章节和官方 TP Verdict 为骨架，不用内部编号替代实验室编号。

### 3.3 第三步：把判据分成三层

这是防止“本地 PASS 冒充官方 PASS”的关键。

| 层级 | 说明 | 当前状态 |
|---|---|---|
| L0 官方 TP 骨架 | 规范、章节、前置、步骤、消息和 Verdict 是否已经落到套件 | 34 条文档齐备，32 条有正文锚 |
| L1 本地可执行证据 | 用真实日志、单测或模拟环境执行字段/行为检查 | 22 条证据入口，21 条 PASS/LIMITED_PASS |
| L2 官方一致性执行 | 由合格 SS 或一致性仪表控制 UE，按官方 TP 给出 P/F | 尚未执行，`OFFICIAL_PASS=0` |

可以概括为：

> L0 是把标准写成可追溯的测试骨架，L1 是本地可执行证据，L2 才是官方法定结论。我们现在完成了 L0，部分完成 L1，L2 还没有条件执行。

## 四、案例一：TC-011 IMS 初始注册

这个案例可以展示“本地已经有真实证据，但仍严格保留官方边界”。

### 4.1 为什么选它

IMS 初始注册是 VoLTE 业务的第一步。只有注册成功，后续主叫、被叫、媒体、保持、会议等业务才有基础。

### 4.2 官方依据

- 主规范：`TS 34.229-1 8.1 Initial registration`。
- 官方正文锚：`34.229-1 V14.7.0` 的 `8.1.1` 到 `8.1.5`。
- 通用流程：`34.229-1 Annex C.2`。
- 默认消息：`34.229-1 Annex A.1.1` 到 `A.1.6`。
- 协议行为：`TS 24.229 5.1.1.2 / 5.1.1.5.1`。
- E-UTRA 前置：`TS 36.508 4.5A.6.3-1`。

### 4.3 官方流程

官方流程不是简单的“发 REGISTER，然后收 200 OK”，而是：

1. UE 先建立 IMS PDN 和 SIP 信令承载。
2. UE 发送未受保护的初始 `REGISTER`。
3. SS 返回带 AKAv1-MD5 challenge 的 `401 Unauthorized`。
4. UE 建立临时安全关联。
5. UE 通过临时安全关联发送第二个带鉴权响应的 `REGISTER`。
6. SS 通过同一安全关联返回 `200 OK`。
7. UE 订阅 registration event package，发送 `SUBSCRIBE`。
8. 网络返回 `200 OK`，并发送 `NOTIFY`。
9. UE 对 `NOTIFY` 返回 `200 OK`。

### 4.4 当前证据

本地真实日志已经观察到：

```text
REGISTER -> 401 Unauthorized -> REGISTER -> 200 OK
```

字段级检查结果是 PASS。

### 4.5 为什么不能直接说官方 PASS

本地日志目前只覆盖官方流程的一部分：

- 缺临时 SA、`Security-Client`、`Security-Verify` 的完整证据；
- 缺 `SUBSCRIBE`、`NOTIFY` 和对应 `200 OK`；
- 缺 HMAC-MD5-96 和 HMAC-SHA-1-96 两轮 PIXIT 配置；
- 未在合格 SS 或一致性仪表上按官方 `.3.2` 执行；
- 没有官方 `TP Verdict`。

所以这个案例的准确表述是：

> TC-011 已建立官方 TP 骨架，本地真实 401 到 200 字段级 PASS。它证明研发行为符合预期，但还不能证明 IMS 初始注册已经通过官方一致性。

## 五、案例二：TC-026 SRVCC

这个案例可以展示“规范和测试结构已经对齐，但必须等真实 L2 环境”。

### 5.1 为什么选它

SRVCC 验证的是 LTE 语音通话过程中，UE 切换到 UTRA 或 GSM CS 域后，语音业务能否保持连续。它涉及 E-UTRA、UTRAN、GERAN、EPC 和 IMS，是典型的高复杂度端到端场景。

### 5.2 官方依据

- 主规范：`TS 36.523-1`。
- 官方章节：
  - `13.4.3.1`：E-UTRA voice 切换到 UTRA CS。
  - `13.4.3.2`：PS voice 加 data 切换到 UTRA。
  - `13.4.3.3`：切换到 GSM CS。
- 关联：
  - `TS 36.508`：跨 RAT 通用测试环境和 IMS MT speech call 前置。
  - `TS 34.108`：UTRA/GERAN 测试系统配置。
  - `TS 23.401`：SRVCC 架构和流程。

### 5.3 官方测试结构

我们已经把官方 `.3.2` 和 `.3.3` 结构拆出来：

- Main behaviour 表；
- Parallel behaviour 表；
- 小区功率和参数变化表；
- `MobilityFromEUTRACommand`；
- `HANDOVER TO UTRAN COMPLETE`；
- `HANDOVER COMPLETE`；
- `ROUTING AREA UPDATE REQUEST`；
- Specific Message Contents 和派生规范。

例如 `13.4.3.1` 的官方判定点包括：

- UE 在 UTRA Cell 5 发送 `HANDOVER TO UTRAN COMPLETE`，TP Verdict 为 `P`；
- 并行流程中 UE 发送 `ROUTING AREA UPDATE REQUEST`，TP Verdict 为 `P`。

### 5.4 当前状态

TC-026 当前是：

```text
STANDARD_ALIGNED / L1_SKELETON
```

不是 PASS，也不是 FAIL，而是已经完成官方结构和消息级骨架，等待真实环境执行。

要进入 L2，至少需要：

- 真实 eNB / EPC；
- UTRA / GERAN 目标网络能力；
- IMS 语音环境；
- 支持跨 RAT 和 SRVCC 的 SS 或一致性仪表；
- 能执行官方 Main behaviour 和 Parallel behaviour 的测试台。

这个案例的准确表述是：

> TC-026 的官方 case、步骤、消息和 Verdict 已经对齐，但当前没有跨 RAT 和仪表环境，所以结果保持 `NOT_EXECUTED`。这不是测试失败，而是不能在没有证据的情况下伪造官方结论。

## 七、当前主要限制

限制要讲具体，不要只说“环境不够”。

1. 缺真实 eNB、EPC、SS、IMS System Simulator 和一致性仪表。
2. TC-013 缺真实 HSS/IMS 注入无效 AKA 挑战。
3. TC-025 的完整 AMR/EVS SCR、SID_FIRST、SID_UPDATE 时序还没有满足。
4. TC-026 到 TC-031 缺 SRVCC、aSRVCC、SSAC、SCM、紧急 IMS、eCall、MSD、SLR 和 PSAP 环境。
5. TC-034 缺具体 YD/T 编号、运营商 VoLTE 入库规范和测试清单。
6. 模拟 IMS 可以证明互通和流程行为，但不能替代 IMS System Simulator 的官方 Verdict。

## 八、结论边界

可以用这四句话收口：

1. 当前成果可以作为自研协议栈的固定验收基线，自研可以基于这套基线启动。
2. 本地 L0/L1 已经可以复跑，用于研发回归和早期发现偏差。
3. 当前不能声称 36.523-1、34.229-1 或第三方入网已经通过。
4. 正式官方 PASS 只能由一致性仪表、合格 SS 或认可检测机构执行后产生。

最重要的边界表述：

> 我们把“验收标准本身”和“最终一致性结论”分开管理。标准、映射、执行框架和本地证据已经形成；官方一致性结论仍必须等 L2 环境。这样既不会耽误自研启动，也不会把本地 PASS 误报成官方 PASS。

## 九、下一步安排

建议按三段讲：

### 第一段：冻结验收基线

冻结 34 条标准套件、机器可读注册表、官方 TP 映射、统一 runner 和证据报告，作为自研开发的版本基线。

### 第二段：接入自研开发流程

每次提交先跑统一 runner，检查：

- 套件和官方映射是否被破坏；
- 本地证据是否回归；
- 受限项是否被误标成 PASS；
- 新增行为是否补齐规范和正文引用。

### 第三段：进入 L2 正式测试

L2 环境到位后，按官方 TP 执行，由合格 SS 或检测机构输出正式 `OFFICIAL_PASS / FAIL`，再叠加运营商入库要求。

## 十、需要公司支持

需要明确支持三类资源：

1. 一致性测试能力：R&S、Anritsu、Keysight 或认可检测机构。
2. 真实环境能力：eNB、EPC、IMS System Simulator、SRVCC、SSAC、紧急呼叫和 eCall 测试台。
3. 入网输入：具体 YD/T 编号、运营商 VoLTE 清单、白皮书和测试规范。

当前没有这些资源，不影响自研启动和 L0/L1 回归，但会影响正式 PASS 的产出时间。

## 十二、现场常见追问

### 问：34 条是不是都已经通过了？

答：34 条标准套件文档已经齐备，本地有 22 条证据复跑，其中 21 条 PASS 或 LIMITED_PASS。官方一致性 PASS 是 0，因为还没有合格 SS 和一致性仪表。

### 问：为什么不用本地 PASS 直接作为最终结论？

答：本地脚本判断的是日志、字段和研发行为是否符合我们写下的断言；官方一致性要求由合格 System Simulator 按官方 TP 控制测试流程并给出 Verdict，两者不是同一层结论。

### 问：这些用例是官方用例的逐字复制吗？

答：不是逐字复制，而是以官方规范和 TP 为骨架建立内部可执行套件。32 条已有正文行号锚，28 条达到精确映射。内部 TC 编号用于研发追溯，正式送审使用官方章节号和 TP Verdict。

### 问：为什么还有这么多受限项？

答：受限项主要缺真实环境或外部输入，例如无效 AKA 注入、跨 RAT、SSAC、eCall、YD/T 和运营商清单。缺证据就标受限，不能强行写成 PASS。

### 问：现在可以开始自研吗？

答：可以。现在冻结的是验收标准、官方映射、执行入口和证据结构，不依赖自研先完成。自研完成后直接按同一套 TC 和官方骨架做回归与 L2 测试。

### 问：这套东西最终怎么降低入网风险？

答：提前把标准、判据、消息和证据入口对齐，避免开发完成后再重做验收标准；后续能用同一套内部编号追溯官方 TC 和运营商用例，减少送审时的返工和对不上号的问题。
