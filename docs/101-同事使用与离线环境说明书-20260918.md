# 同事使用与离线环境说明书

> 适用对象：拿到 `lte-verification` 私有仓库后，需要复核现有结果、接手标准
> 例程，或准备在另一台服务器验证新 DUT 的同事。
>
> 核心结论：仓库可以放在任意目录，不需要修改项目路径。只要机器有 Git 和
> Python 3.10+，就能校验标准原文包、复跑仓库中已经固化的黄金证据并得到与
> 原工作区一致的结果。没有 IMS/EPC/eNB/仪表时，不能把本地结果升级成官方
> 一致性结论。

## 1. 最短使用路径

### 1.1 Windows

```powershell
git clone https://github.com/xiongqian-a/lte-verification.git
cd lte-verification
.\bootstrap.cmd --doctor
.\bootstrap.cmd --verify-standards
.\bootstrap.cmd --colleague-replay
python -X utf8 runners\verify_portable_install.py --full
```

### 1.2 Linux/macOS

```sh
git clone https://github.com/xiongqian-a/lte-verification.git
cd lte-verification
chmod +x bootstrap.sh
./bootstrap.sh --doctor
./bootstrap.sh --verify-standards
./bootstrap.sh --colleague-replay
python3 -X utf8 runners/verify_portable_install.py --full
```

### 1.3 交接验收通过标志

```text
STANDARDS BUNDLE: PASS
FILES: 45
TOTAL BYTES: 144416074
COLLEAGUE REPLAY: PASS
COMMIT_MATCH: True
TC011_INVARIANTS: PASS
OFFICIAL_VERDICT: null
PORTABLE INSTALL: PASS (FULL)
UNIFIED RUNNER: PASS FROM UNRELATED CWD
```

这些标志只证明仓库快照、标准原文包、checker 和历史证据可以复现，不证明已经
重新连接真实 eNB/EPC/IMS，也不产生官方 `36.523-1`、`34.229-1` 或第三方
入网 Verdict。

## 2. 为什么不需要修改文件路径

仓库中的入口、checker、标准包校验器和报告生成器都从脚本自身位置计算仓库根
目录，例如：

```python
ROOT = Path(__file__).resolve().parent.parent
```

因此下面这些位置都可以直接运行：

```text
C:\work\lte-verification
D:\handoff\lte-verification
/home/colleague/repos/lte-verification
/opt/verification/lte-verification
```

前提是从仓库根目录启动 `bootstrap`，或者使用脚本的完整路径启动。不要修改：

- `registry/`、`suites/` 或 `standards/official/manifest.json` 中的相对路径；
- `runners/` 中的仓库根目录计算逻辑；
- 原机器没有、同事机器也不需要的盘符或用户目录；
- `generated/` 中的报告来绕过失败。

仓库不在原路径、用户名不同、盘符不同、clone 目录名不同，都不需要改代码。

## 3. 3GPP 原文包当前放在哪里

标准原文位于：

```text
standards/official/
```

清单和哈希位于：

```text
standards/official/manifest.json
```

当前包统计：

```text
文件数：45
规范目录数：39
总字节数：144416074
```

它包含当前 `suites/` 和 `registry/` 直接引用的 3GPP/ETSI 标准版本，以及
`RFC 3261`、`RFC 3515`。主要覆盖：

- LTE/EPC 官方 TP：`36.523-1`、`36.523-2`；
- IMS 官方 TP：`34.229-1`、`34.229-2`；
- IMS/SIP/补充业务：`24.229`、`24.147`、`24.173`、`24.237`、
  `24.341`、`24.605`、`24.610`、`24.628`、`24.629`；
- NAS/核心网：`22.101`、`23.003`、`23.060`、`23.401`、`24.008`、
  `24.301`、`29.228`；
- 媒体/eCall：`26.093`、`26.114`、`26.193`、`26.267`、`26.450`、
  `26.451`；
- 安全：`33.102`、`33.203`、`33.401`；
- RAN/测试环境：`34.108`、`36.306`、`36.323`、`36.331`、`36.508`、
  `36.509`、`44.018`、`51.010-1`。

### 3.1 “当前套件直接引用的全部原文”不等于“3GPP 全部规范”

3GPP 规范目录包含大量文档，不可能也不应该在没有明确用途和再分发授权的情况下
把整个目录全部塞入仓库。本仓库采用的正确口径是：

```text
当前 34 条 TC 和 registry 直接引用到的标准版本，已随仓库交付；
未引用到的其他 3GPP 规范，不默认属于本套件。
```

目前明确没有纳入或无法仅靠仓库补齐的是：

- 具体 YD/T 送测标准编号；
- 运营商 VoLTE 入库企标和准入清单；
- 后续新增 TC 才需要使用、当前尚未直接引用的其他 3GPP 规范；
- 合格 SS/仪表/检测机构内部使用的测试配置、许可和校准数据。

如果后续新增 TC，必须先给出规范编号、Release、章节和用途，再补原文、更新
`manifest.json`，然后重新核对引用。不能拿相近版本或相近章节代替。

### 3.2 标准包校验

```sh
python -X utf8 runners/verify_standards_bundle.py
```

必须得到：

```text
STANDARDS BUNDLE: PASS
FILES: 45
TOTAL BYTES: 144416074
```

如果校验失败，先恢复文件或重新 clone，不要为了“消除报错”修改 hash。

### 3.3 再分发限制

该目录只允许在已授权的私有组织内部交接。不要把仓库改成公开仓库，也不要把
标准 PDF、DOC、DOCX 上传到公共网盘、公共 GitHub 或组织外。公开前必须逐份
确认再分发许可，并在必要时移除标准原文和敏感证据。

## 4. 黄金证据复跑和新 DUT 验证的区别

| 任务 | 是否需要实时 eNB/EPC/IMS/仪表 | 使用的输入 | 正确结论 |
|---|---|---|---|
| 交接复核现有基线 | 不需要 | 仓库固定 commit 和已提交黄金证据 | 仓库可复现、历史 checker 结果一致 |
| 验证同事修改后的 DUT | 需要实时测试台和新日志 | 新 DUT commit、二进制、实时日志/抓包 | `FRESH_DUT` 本地或测试床证据 |
| 官方一致性测试 | 必须有合格 SS/实验室 | 官方 TP、合格仪表和实验室配置 | `OFFICIAL_PASS` / `OFFICIAL_FAIL` |

黄金证据复跑可以使用 `evidence/` 中的旧日志，因为其目的就是验证这份固定快照
能否复现。

验证同事修改后的协议栈时，不能使用旧日志：

1. 记录新 DUT 源码 commit 和二进制 SHA256；
2. 从新构建重新产生 SIP/SDP/RTP/媒体/抓包日志；
3. 输出到新的 `outputs/fresh-dut-<日期>/`；
4. 报告标记 `EVIDENCE_SOURCE: FRESH_DUT`；
5. 旧日志只用于基线回归，不作为新代码结果；
6. 即使 fresh-DUT 本地通过，仍不是官方一致性 Verdict。

## 5. 另一台服务器缺少软件和环境时怎么办

### 5.1 先诊断

```sh
python -X utf8 runners/environment_doctor.py
```

或：

```powershell
.\bootstrap.cmd --doctor
```

重点读取：

```text
GOLDEN_REPLAY_READY
CHECKER_ONLY_READY
FRESH_DUT_ENV_READY
FRESH_DUT_ENV_MISSING
OFFICIAL_SS_REQUIRED
OFFICIAL_SS_DETECTED
```

### 5.2 按任务判断是否能继续

| 缺失环境 | 校验标准/映射 | 复跑黄金证据 | 重新跑实时端到端 |
|---|---:|---:|---:|
| Docker | 可以 | 可以 | 取决于测试床是否要求 Docker |
| Open5GS/EPC | 可以 | 可以 | 不可以 |
| srsRAN/eNB | 可以 | 可以 | 不可以 |
| IMS/OpenIMSCore | 可以 | 可以 | 不可以 |
| pjsua/目标 UE | 可以 | 可以 | 不可以 |
| tshark/Wireshark | 可以 | 可以 | 不能完成新抓包字段核对 |
| ffmpeg/媒体工具 | 可以 | 可以 | 不能完整核对媒体、DTX/SID |
| R&S/Anritsu/Keysight/实验室 | 可以 | 可以 | 不能生成官方 Verdict |

缺少这些系统不会阻止仓库校验和历史证据复跑，但必须把新的实时端到端结果保持
为 `RESTRICTED`、`NOT_EXECUTED` 或 `L2_REQUIRED`。

### 5.3 没有 Python

Windows 先运行 `bootstrap.cmd`；它会尝试通过 `winget` 安装 Python 3.12。
Linux/macOS 先运行 `bootstrap.sh`；它会按系统包管理器尝试安装 Python。

如果服务器禁止安装软件：

- 让管理员从发行版仓库提供 Python 3.10+；
- 或在一台具备 Python 3.10+ 的机器上执行交接复跑；
- 或只做文件级查看，但此时不能产生可追溯的运行结论。

### 5.4 没有 Git

可以在另一台有 Git 的机器导出 Git bundle：

```sh
git bundle create lte-verification.bundle --all
git bundle verify lte-verification.bundle
```

目标服务器有 Git 后：

```sh
git clone lte-verification.bundle lte-verification
cd lte-verification
git rev-parse HEAD
```

如果目标服务器既没有 Git，也不能安装 Git，可以解压包含 `.git/`、
`standards/` 和 `evidence/` 的完整仓库压缩包，但无法可靠核对固定 commit 的
Git 元数据。

### 5.5 没有核心网、IMS、pjsua、抓包或媒体工具

仍然可以完成：

```sh
python -X utf8 runners/verify_standards_bundle.py
python -X utf8 run_official_suite.py
python -X utf8 runners/colleague_replay_verification.py --expected-commit <hash>
python -X utf8 runners/verify_portable_install.py --full
```

不能完成或不能声称完成：

- 新的 eNB/EPC/IMS 端到端执行；
- 新 DUT 的实时注册、呼叫、媒体、切换、错误注入；
- 真实 IPsec、SUBSCRIBE/NOTIFY 或 IMS 恢复流程；
- `36.523-1`、`34.229-1` 或第三方入网官方判定。

Open5GS、srsRAN、OpenIMSCore、FreeSWITCH、Asterisk 或 pjsua 只能做 L1
功能测试，不能替代合格 SS 或检测机构。

### 5.6 没有仪表或检测机构

输出必须保持：

```text
OFFICIAL_VERDICT: null
```

只有在合格 SS/实验室实际执行对应官方 TP 并提供 Verdict 后，才允许填写
`OFFICIAL_PASS` 或 `OFFICIAL_FAIL`。

## 6. 仓库常用命令

| 命令 | 用途 |
|---|---|
| `.\bootstrap.cmd --doctor` | 检查本机可复跑、可实时测试和官方仪表能力 |
| `.\bootstrap.cmd --verify-standards` | 校验标准原文包路径、大小和 SHA256 |
| `.\bootstrap.cmd --colleague-replay` | 固定 commit、统一 runner、TC-011 不变量和黄金证据复跑 |
| `python -X utf8 run_official_suite.py` | 完整运行仓库本地基线 |
| `python -X utf8 run_official_suite.py --skip-evidence` | 只做映射、自检和报告检查 |
| `python -X utf8 runners\verify_portable_install.py --full` | 从无项目路径依赖的方式执行完整便携性检查 |

## 7. 结果词和边界

| 结果 | 含义 |
|---|---|
| `LOCAL_PASS` | 本地输入满足 checker 判据，只是研发实现证据 |
| `LIMITED_PASS` | 核心行为通过，但变体、字段或真实环境未覆盖 |
| `SELFCHECK_PASS` | checker 本身正控和负控通过 |
| `STANDARD_ALIGNED` | 官方步骤和判据已映射，尚未完整执行 |
| `RESTRICTED` | 缺标准、环境、权限或外部输入 |
| `NOT_EXECUTED` | 没有该官方章节的合格证据 |
| `OFFICIAL_PASS` / `OFFICIAL_FAIL` | 只能由合格 SS、仪表或实验室产生 |

严禁把 `LOCAL_PASS`、`LIMITED_PASS` 或 `SELFCHECK_PASS` 改成
`OFFICIAL_PASS`。

## 8. 常见问题

### 8.1 同事机器路径完全不同

不用改路径。只要保证仓库目录完整，从仓库根目录运行入口即可。

### 8.2 clone 后提示找不到标准文件

检查 `standards/official/` 是否存在，执行：

```sh
python -X utf8 runners/verify_standards_bundle.py
```

如果失败，重新 clone 或恢复缺失文件，不要只修改 manifest。

### 8.3 脚本 PASS，但需要说明这是不是官方一致性

正确回答是：

```text
本地 PASS 只代表研发行为符合当前标准对齐 checker，不等于 36.523-1 或
34.229-1 官方一致性。官方结论只能来自合格 SS、仪表或检测机构。
```

### 8.4 同事要验证新自研代码

先完成黄金证据复跑，确认基线稳定；再为 DUT 建立独立 fresh-DUT 目录、实时
测试台和新日志。不要把旧 `evidence/` 日志作为新代码结果。

### 8.5 要补更多 3GPP 原文

提供规范编号、Release、版本、用途和引用 TC，然后重新生成 manifest 并校验。
不要用相近版本代替指定版本，也不要把包含全部 3GPP 规范当作当前仓库的承诺。
