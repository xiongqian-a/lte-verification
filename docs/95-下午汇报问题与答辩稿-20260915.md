# 下午汇报问题与答辩稿

> 配套汇报稿：`94-下午汇报稿-模块与案例版-20260915.md`
>
> 回答口径：当前成果是“官方 TP 对齐的可执行验收基线”，不是官方一致性执行记录。本地 PASS 不等于 36.523-1 / 34.229-1 官方一致性，也不等于第三方入网通过。

## 一、回答总原则

现场回答时坚持三句话：

1. 已经完成的，说清楚完成在哪一层。
2. 没有执行的，明确是 `RESTRICTED` 或 `NOT_EXECUTED`，不能包装成 PASS。
3. 正式官方结论只认合格 SS、一致性仪表或检测机构按官方 TP 给出的 Verdict。

如果问题一时不好回答，可以先用这句话稳住口径：

> 这个问题要分两层看：验收标准已经做到哪一层，正式官方执行还需要什么条件。我们现在完成的是标准套件、官方 TP 映射、本地证据和 L2 接口；正式官方 PASS 还没有执行。

## 二、目标与价值

### 问 1：这次工作到底交付了什么？

答：交付了一套面向自研协议栈的验收基线，包括 34 条标准套件文档、官方规范和 TP 映射、机器可读注册表、统一 runner、本地证据，以及后续接一致性仪表和检测机构的 L2 接口。

可以直接概括为：

> 交付的不是一块已经通过认证的协议栈，而是一套后续自研完成后可以直接使用的标准验收尺子。

### 问 2：为什么在没有官方仪表的情况下还要做这些？

答：因为验收标准可以先定，正式 Verdict 必须后做。如果等仪表到位才开始整理标准和用例，前面开发完的协议栈还要重新对标准、重做映射，返工成本更高。

现在先把标准、官方章节、测试步骤、消息判据和证据入口固定下来，后续仪表到位后可以直接进入 L2。

### 问 3：这套工作最终怎么降低第三方入网风险？

答：主要有四点：

- 提前发现功能和协议覆盖缺口；
- 每条实现差异可以回溯到具体规范和章节；
- 内部 TC 与官方 TC、TP Verdict 建立映射，送审时不容易对不上号；
- 自研栈可以先用 L0/L1 回归，减少正式测试阶段才暴露大量问题。

### 问 4：现在可以开始自研协议栈开发吗？

答：可以。当前冻结的是验收基线、官方映射、执行框架和证据入口，不依赖自研先完成。自研完成后，用同一套 TC 和官方规范做回归，再进入 L2。

### 问 5：这是不是一个已经完成的项目？

答：当前阶段已经达到“可以冻结验收基线并支持自研启动”的完成标准。若完成标准定义为“取得 36.523-1、34.229-1 或第三方入网的官方 PASS”，则还没有完成，因为当前没有合格一致性仪表、IMS SS 和检测机构环境。

### 问 6：如果这只是验收基线，价值会不会不够大？

答：它的价值在于把后续开发、回归和送审的路径固定下来。缺少这一步，开发后期会出现标准不统一、编号无法追溯、本地 PASS 被误当官方 PASS 等问题。现在先把标准层做稳，能直接减少后续返工和沟通成本。

## 三、两个实际案例

### 问 7：为什么选 TC-011 IMS 初始注册作为案例？

答：IMS 初始注册是 VoLTE 业务的第一步，后续呼叫、媒体、保持和会议都建立在注册成功之上。它又能同时说明本地已经有真实证据，以及为什么本地证据仍不等于官方一致性。

### 问 8：TC-011 现在到底通过没有？

答：本地真实日志已经观察到：

```text
REGISTER -> 401 Unauthorized -> REGISTER -> 200 OK
```

原始日志中的字段级子集检查为 PASS，但 TC-011 的总体状态仍是 `LIMITED_PASS` / `L1_LOCAL_SIMULATED`；`official_verdict=null`，官方一致性还没有 PASS。

### 问 9：既然已经收到 200 OK，为什么还不能算官方通过？

答：因为官方 `34.229-1 8.1` 的最终 P/F 必须由合格 SS 按官方流程执行并给出 TP Verdict。当前真实日志和 L1 参考仿真已经覆盖 C.2 Steps 4-11、`Security-Client`、`Security-Verify`、`SUBSCRIBE`、`NOTIFY` 和双 PIXIT 算法，但仍缺真实内核 `xfrm`/ESP、真实 DUT/SS，以及官方 SS Verdict。

### 问 10：TC-011 还缺哪些具体证据？

答：本地层面已经补齐 C.2 Steps 4-11、Security Header、`SUBSCRIBE`/`NOTIFY` 和两轮 HMAC PIXIT。当前主要缺：

- 真实 Linux `xfrm` 状态/策略及 ESP/AH 数据面证据；
- 真实 DUT 或 UE 新栈在真实 SS 下的执行记录；
- 真实 eNB/EPC/IMS、无线接口和 USIM/ISIM 前置；
- 合格 SS 的 Test Procedure 原始记录和 TP Verdict。

### 问 11：为什么选 TC-026 SRVCC 作为第二个案例？

答：SRVCC 是高复杂度跨 RAT 场景，涉及 LTE、UTRA/GERAN、EPC 和 IMS。它很适合说明“官方规范和步骤已经对齐，但真实环境不足时只能保持 NOT_EXECUTED”。

### 问 12：TC-026 现在做到什么程度？

答：已经锚定到 `36.523-1 13.4.3.1 / 13.4.3.2 / 13.4.3.3`，并拆出了 Main behaviour、Parallel behaviour、`.3.3` Specific Message Contents 和相关 Verdict。

当前状态是：

```text
STANDARD_ALIGNED / L1_SKELETON
```

不是 PASS，也不是 FAIL，而是等待真实 L2 环境执行。

### 问 13：TC-026 为什么不能先用模拟器跑？

答：普通模拟器可以提供部分网络互通，但不能提供官方一致性要求的跨 RAT 无线环境、SS 精确控制和官方 TP Verdict。它可以做研发预验证，不能替代正式一致性结论。

### 问 14：TC-026 要真正执行，需要什么？

答：至少需要真实 eNB/EPC、UTRA/GERAN 目标网络能力、IMS 语音环境、支持 SRVCC 和跨 RAT 的 SS 或一致性仪表，以及能执行官方 Main behaviour 和 Parallel behaviour 的测试台。

## 四、模块与范围

### 问 15：为什么是 34 条，不是官方案例的全部？

答：34 条是内部功能追溯范围，覆盖 8 个模块，不是官方一致性用例总数的替代品。我们保留内部编号方便研发管理，同时逐条映射到官方规范、章节或 TP。正式送审以官方 TC、章节和 TP Verdict 为骨架。

### 问 16：8 个模块分别做什么？

答：

| 模块 | 主要能力 |
|---|---|
| EPS / EPC / 承载 | Attach、PDN、IMS APN、默认和专用承载、释放、拒绝和退避 |
| IMS / SIP / 呼叫 | 注册、鉴权、重注册、恢复、主叫、被叫、保持、会议、REFER |
| 媒体 / SDP / VAD-DTX | SDP 协商、音频媒体、长稳、AMR/EVS VAD/DTX |
| SRVCC / aSRVCC | LTE 语音向 UTRA/GSM CS 域切换和语音连续性 |
| SSAC / SCM | 接入控制和 SIB2/RRC 相关行为 |
| 紧急呼叫 / eCall | 紧急 IMS 呼叫、MSD、SLR、PSAP |
| 错误码 / 定时器 | 503、504、超时和恢复 |
| 中国入网 | YD/T 和运营商 VoLTE 入库要求 |

### 问 17：这 34 条是不是官方案例的逐字复制？

答：不是逐字复制，而是以官方规范和 TP 为骨架建立内部可执行套件。对能够核到正文的条目保留章节和行号锚；对官方没有独立 TP、只有行为要求的部分，明确标记为 `behavior` 或 `partial`，不冒充官方独立一致性 TC。

### 问 18：为什么有些模块现在还没有可执行脚本？

答：因为部分模块缺真实环境，例如 SRVCC、SSAC、eCall、紧急 IMS 和运营商入网。没有环境时可以先完成官方 TP 骨架、消息结构、L2 Schema 和适配器，但不会伪造执行结果。

### 问 19：为什么官方 36.523-1 里没有独立的 IMS 呼叫用例？

答：不同 IMS 行为归不同规范。IMS UE 一致性主要看 `34.229-1`，SIP 协议行为看 `24.229`，媒体和 SDP 还要交叉到 `26.114` 等。`36.523-1` 中部分紧急和 eCall 场景会引用 `34.229-1` 的通用 IMS 流程，但不能因此把 IMS 呼叫全部算到 36.523-1。

### 问 20：为什么有的 TC 有官方 ID，有的没有？

答：因为不是每个内部功能点都存在独立的官方一致性 TC。对于没有独立官方 TP 的行为，我们保留为研发行为或健壮性验证，并明确说明不能用它替代官方一致性 case。

## 五、官方对齐与标准正确性

### 问 21：怎么保证条款号不是凭记忆或推测写出来的？

答：能核到正文的条目已经建立正文行号锚，当前 32 条有正文锚，其中 28 条是 `exact_line_ref`。每条的规范、版本、章节、正文位置和抽取文件都保留记录。无法精确对应的条目不会写成精确映射。

### 问 22：能不能保证每一条都逐字核到官方原文？

答：不能把 `partial`、`behavior` 或外部依赖项说成逐字核准。当前 28 条达到精确映射，其余如实标记。正式送审前仍应继续把能核的条目推进到 `.3.2` 子例级和消息级。

### 问 23：如果实验室拿过去发现条款号对不上怎么办？

答：当前映射保留规范名、版本、章节和正文行号，可以快速定位并修正。对于没有独立官方 TC 或仍在 `partial` 的条目，已经显式标记，不会在送审时伪装成官方 ID。

### 问 24：为什么 34.229-1 使用 V14.7.0，而不是后面拿到的 V14.8.0？

答：因为 V14.8.0 已把测试要求指向 Release 15，并将 `5 to 22` 和 Annex A 到 J 标为 Void。当前 Release 14 的正文主锚必须使用 V14.7.0，不能拿 V14.8.0 强行重锚行号。

### 问 25：`exact_line_ref`、`partial`、`behavior` 分别是什么意思？

答：

- `exact_line_ref`：已经能锚到官方规范正文的具体行号或明确章节。
- `partial`：有规范支撑，但覆盖不完整，或官方没有独立的完整一致性 case。
- `behavior`：官方没有独立 TP，保留为研发行为、鲁棒性或功能验证。
- `none`：当前缺外部输入，例如 TC-034 缺 YD/T 和运营商清单。

### 问 26：官方用例中的容差、变体和 Specific Message Contents 怎么处理？

答：能在正文和 `.3.3` 中抽到的内容会保留在官方 TP 骨架和机器可读库中。以 TC-026 到 TC-031 为例，已经结构化 11 个章节、114 个消息检查点、22 个 Verdict 和 77 个 Specific Message Contents 表。但由于没有 L2 证据，当前全部保持 `NOT_EXECUTED`。

### 问 27：如果规范升级了，这套基线会不会失效？

答：规范升级需要做版本变更，不会直接覆盖旧行号。正确做法是明确目标 Release，重新核对新增或变化章节，更新映射并保留变更记录。当前 Release 14 的 34.229-1 版本边界已经有自动校验。

## 六、本地证据与结果

### 问 28：本地到底跑了多少条？

答：本地证据复跑 22 条，其中：

- `PASS`：19 条；
- `LIMITED_PASS`：2 条；
- `EXPECTED_FAIL`：1 条；
- 非预期 `FAIL`：0 条。

### 问 29：为什么是 21 条 PASS 或 LIMITED_PASS，不是 22 条？

答：因为还有 1 条是预期的负控。TC-013 使用真实 bad-key 日志验证 checker 是否能够识别不符合官方要求的认证行为，返回 `EXPECTED_FAIL` 是预期结果，不是产品通过。

### 问 30：23 个脚本自检全部通过，能说明什么？

答：只能说明判定脚本能够执行，正控和负控路径能够触发，脚本本身没有明显运行问题。它不证明产品达到官方一致性。

### 问 31：本地 PASS 到底代表什么？

答：表示本地日志、报文、字段或代码行为符合脚本中的研发断言。它可以作为开发回归证据，但不能作为 36.523-1、34.229-1 或第三方入网结论。

### 问 32：本地 PASS 能代表 pjsua 新栈合规吗？

答：不能。当前证据主要验证行为、字段或流程符合预期，不等于完整的协议栈一致性，也不等于新栈已经满足所有规范和运营商要求。

### 问 33：为什么有本地 PASS，但官方 PASS 还是 0？

答：因为两者不是同一个判定主体。本地 PASS 来自我们的脚本和日志检查；官方 PASS 必须由合格 SS 或一致性仪表按照官方 TP 控制流程并输出 Verdict。

### 问 34：有没有隐藏失败？

答：当前本地复跑没有非预期 FAIL。`RESTRICTED`、`NOT_EXECUTED` 和 `EXPECTED_FAIL` 都显式保留，没有转换成 PASS。

### 问 35：证据能不能审计和复跑？

答：可以。当前有统一 runner、机器可读注册表、本地证据矩阵、官方 TP 抽取、行号校验脚本和官方风格状态报告。运行后可以重新生成状态和报告。

## 七、限制、环境与风险

### 问 36：目前最主要的限制是什么？

答：缺真实 eNB、EPC、SS、IMS System Simulator 和一致性仪表；TC-013 缺无效 AKA 挑战注入；TC-025 缺完整 AMR/EVS SCR/SID 时序；TC-026 到 TC-031 缺跨 RAT、SSAC、紧急和 eCall 环境；TC-034 缺 YD/T 和运营商清单。

### 问 37：为什么有这么多 `RESTRICTED`，是不是项目没做完？

答：`RESTRICTED` 表示外部依赖不足，不能输出正式结论，不等于失败。当前设计就是不让缺证据项目自动升级为 PASS。这样后续资源到位后，可以继续在同一套结构里补证据。

### 问 38：能不能用 srsRAN、Open5GS、OpenIMSCore 或 FreeSWITCH 代替官方环境？

答：可以用于研发互通、流程预验证和 L1 行为证据，但不能替代官方一致性 SS 或 IMS System Simulator 的 Verdict。它们的用途和正式测试层级不同。

### 问 39：TC-013 为什么现在只能做预期失败负控？

答：因为官方场景要求 IMS/HSS 注入 MAC 参数无效或 SQN out of range 的挑战。当前环境没有这种真实注入能力，不能把普通 bad-key 日志冒充官方无效 AKA 场景。

### 问 40：TC-025 的 VAD/DTX 为什么还是 LIMITED_PASS？

答：当前可以观察到部分 SID 和静默帧行为，但完整 AMR/EVS source-controlled rate、SID_FIRST、SID_UPDATE 周期和官方 SCR 断言还没有全部满足，因此不能升级为标准符合 PASS。

### 问 41：TC-034 为什么没有官方编号？

答：因为 YD/T 和运营商 VoLTE 入库要求不是通用的 3GPP TC。它必须使用具体标准编号和运营商清单。当前没有这些输入，所以保持外部依赖状态，不能自行编造。

### 问 42：当前最大风险是什么？

答：最大风险不是本地脚本失败，而是：

- 把本地 PASS 误当官方一致性；
- 到送审阶段才发现 L2 环境和仪表资源没有准备；
- 规范版本变化后没有重新映射；
- 运营商清单和 YD/T 输入迟迟没有确定。

### 问 43：如果第三方实验室认为我们的用例和官方不一致，怎么处理？

答：以官方规范和检测机构判定为准。内部 TC 编号只用于追溯；正式测试用官方 TC、章节、`.3.2` 步骤和 TP Verdict。发现差异时回到规范正文重新核对并更新映射，不用内部编号掩盖差异。

## 八、下一步、资源和排期

### 问 44：下一步最优先做什么？

答：先冻结第一版验收基线，再把它接入自研开发和每轮回归。同时启动 L2 测试资源确认，包括一致性仪表、检测机构、IMS SS 和真实网络环境。

### 问 45：需要公司提供什么支持？

答：需要三类资源：

1. 一致性测试资源：R&S、Anritsu、Keysight 或认可检测机构。
2. 真实网络资源：eNB、EPC、IMS System Simulator、SRVCC、SSAC、紧急呼叫和 eCall 测试台。
3. 入网输入：具体 YD/T 编号、运营商 VoLTE 清单、白皮书和测试规范。

### 问 46：必须要买仪表吗，能不能租或用检测机构？

答：可以使用认可检测机构或外部一致性实验室，不一定要购买仪表。关键是环境必须合格，能够按官方 TP 控制 UE 并输出正式 Verdict。

### 问 47：没有 L2 环境，后续工作会不会停？

答：不会。自研开发、本地 L0/L1 回归、官方映射收紧、测试框架补强和 L2 适配器可以继续推进。受影响的是正式官方 PASS 的产出时间，不是开发启动本身。

### 问 48：后续怎么判断自研协议栈达到要求？

答：不建议用内部 TC 数量判断。建议按项目节点看：

1. 开发实现是否对应官方规范和正文锚；
2. 本地 L0/L1 回归是否稳定通过；
3. 受限项是否随着环境补入逐步减少；
4. L2 是否由合格 SS 或检测机构输出官方 Verdict；
5. 运营商入库项是否覆盖具体 YD/T 和运营商清单。

### 问 49：怎么保证自研过程中不走偏？

答：每次提交执行统一 runner，检查套件、官方映射、本地证据和受限标记；任何新增行为必须补充官方依据或明确标为研发行为。不能为了跑出 PASS 修改官方判据。

### 问 50：最终给领导看的验收结果应该是什么？

答：最终结果应该分两栏：

- 标准与本地回归结果：说明覆盖、证据、受限项和非预期失败；
- L2 官方结果：由一致性仪表或检测机构给出 `OFFICIAL_PASS / FAIL`。

不能把两栏合并成一个“通过率”。

## 九、尖锐问题

### 问 51：这些标准条款是不是你自己想出来的？

答：不能这样概括。能核到正文的条目已经保留了规范版本、章节和行号锚，当前 32 条有正文锚，28 条是精确映射。与此同时，`partial`、`behavior` 和外部依赖项也明确保留，不把未核内容说成已终核。

### 问 52：之前只做本地脚本，是不是耽误了时间？

答：前期工作有价值，但不能停在本地方案上。现在这套版本已经把本地执行结果和官方标准分层，补齐了官方 TP 骨架、行号证据和 L2 接口。后续继续开发时，不需要推翻内部 TC，只需要在同一编号下持续收紧官方映射和补 L2 证据。

### 问 53：为什么一开始不直接做官方 TP？

答：官方 TP 要落到可执行验收基线，需要先确定规范版本、抽取章节、建立映射、准备环境，再接入仪表。前面的本地工作解决了一部分功能观察和脚本问题；当前阶段已经把这些结果重新归档到官方 TP 框架下，而不是丢掉重来。

### 问 54：没有官方 PASS，这套结果是不是没有意义？

答：有意义，但只能按它的层级使用。它不能证明产品已经通过一致性，但可以证明验收标准、官方映射、执行框架和证据入口已经建立。对自研早期回归和后续送审准备有直接价值。

### 问 55：会不会为了汇报把受限项说成完成？

答：不会，也不能这样做。当前明确保留 `RESTRICTED`、`NOT_EXECUTED` 和 `EXPECTED_FAIL`。官方一致性 PASS 是 0，第三方入网 PASS 也是 0，这个结论不能因为汇报需要而改写。

### 问 56：如果只允许用一句话总结，怎么说？

答：当前已经形成一套可冻结、可追溯、可复跑、可接入正式仪表的自研协议栈验收基线，但还没有取得官方一致性和第三方入网 PASS。

## 十、绝对不要说的话

- 不要说“36.523-1 一致性已经通过”。
- 不要说“34.229-1 IMS 一致性已经通过”。
- 不要说“本地 PASS 就是官方 PASS”。
- 不要说“本地 PASS 代表 pjsua 新栈合规”。
- 不要说“模拟 IMS 等于 IMS System Simulator”。
- 不要说“第三方入网已经通过”。
- 不要把 `NOT_EXECUTED`、`RESTRICTED` 或 `EXPECTED_FAIL` 描述成 PASS。
- 不要把内部 34 条 TC 直接说成 34 条官方一致性用例。

> 当前工作解决的是验收标准、官方映射、执行框架和本地证据基线问题。自研启动不受影响，后续可以先用 L0/L1 做回归；真正的 36.523-1、34.229-1 和第三方入网结论，必须等合格 SS、一致性仪表、IMS System Simulator 和检测机构按官方 TP 执行。我们不会把没有 L2 证据的结果写成官方 PASS。
