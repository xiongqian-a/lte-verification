# 同事拉取复跑与结果验收流程

> 目的：让第一次拿到仓库的同事，不需要当前会话记忆、不需要改项目路径，
> 按说明书从固定 commit 复跑并检查这套验证例程。
>
> 边界：同事复跑可以验证仓库可复现性、标准映射、脚本判据和已提交证据；
> 没有合格 SS、仪表或检测机构时，仍然不能产生官方一致性 Verdict。

## 1. 先准备什么

同事只需要拿到：

1. GitHub 仓库和固定的 full commit hash，不使用“main 最新”作为复跑目标。
2. 一份全新的 clone，不复用当前工作区，避免本地改动影响结果。
3. 可以读取该仓库的本机环境和 Git。
4. 明确结果边界：本地 `PASS` 不能写成 `OFFICIAL_PASS`。

同事不需要配置服务器、核心网、IMS、项目路径或第三方 Python 依赖。Python
3.10+ 缺失时，Windows 可运行 `bootstrap.cmd`，Linux/macOS 可运行
`bootstrap.sh`，由仓库脚本负责准备 Python 并进入统一 runner。

直接复跑基线不需要另外提供规范 PDF/DOC/DOCX。仓库已经带有标准映射、抽取
片段、证据，以及当前套件已收集到的标准原文包 `standards/official/`。同事先
运行 `.\bootstrap.cmd --verify-standards`；只有输出
`STANDARDS BUNDLE: PASS`，才能把当前 checkout 当成同一份原文快照做人工
条款和行锚核对。

标准包不是 3GPP 全部规范。当前 45 个文件已经覆盖仓库现有 `suites/` 和
`registry/` 直接引用的 3GPP/ETSI TS，以及 `RFC 3261`、`RFC 3515`；版本、用途
和剩余外部依赖见 `standards/README.md`。缺失项不能通过改报告或拿相近版本替代
来消掉。

## 2. 最短执行方式

在全新目录克隆：

```powershell
git clone https://github.com/xiongqian-a/lte-verification.git C:\verify-lte
cd C:\verify-lte
git checkout <full-commit-hash>
```

先确认 checkout：

```powershell
git status --short --branch
git rev-parse HEAD
git remote -v
```

Windows 一条命令复跑：

```powershell
.\bootstrap.cmd --colleague-replay
```

Linux/macOS 一条命令复跑：

```sh
chmod +x bootstrap.sh
./bootstrap.sh --colleague-replay
```

如果本机已经有 Python 3.10+，也可以直接运行：

```powershell
python -X utf8 runners/colleague_replay_verification.py `
  --expected-commit <full-commit-hash> `
  --out-dir outputs/colleague-replay
```

复跑报告和机器可读结果会写到：

```text
outputs/colleague-replay/colleague-replay-<timestamp>.md
outputs/colleague-replay/colleague-replay-<timestamp>.json
```

脚本会执行：

- 统一 runner；
- registry 与 34 条套件元数据一致性；
- 全部 checker 自检；
- 已固化本地证据复跑；
- TC-011 注册流自检；
- TC-011 L1 IPsec/SUBSCRIBE/NOTIFY 自检；
- TC-011 必须保持 `LIMITED_PASS / L1_LOCAL_SIMULATED`、`official_verdict=null`；
- 关键 artifact SHA256；
- 运行前后 Git 状态和 diff stat。

成功输出必须包含：

```text
COLLEAGUE REPLAY: PASS
TC011_INVARIANTS: PASS
OFFICIAL_VERDICT: null
```

该 `PASS` 是“同事复跑成功、固定提交匹配、仓库内部一致性检查通过”，不是协议
一致性结论。

这条路径使用仓库中已经提交的日志、抓包和 checker，不会自动连 eNB/EPC/IMS，
也不会生成新的现场原始日志。如果同事需要“自己产生一套新日志”，必须另外接入
实时测试环境。

## 3. 同事还必须人工检查什么

自动化脚本只能覆盖仓库内部一致性，不能替代标准审查。同事还必须继续做：

1. 对照规范原文抽查 registry 和 TC 文档中的 clause、line anchor、消息字段、
   前置条件和 TP Verdict。
2. 检查 checker 的正控、负控和合成 fixture，确认不是“脚本生成输出后再由
   同一脚本给自己判 PASS”。
3. 对每条本地证据追溯原始日志、抓包或测试台输出，确认输入不是临时伪造。
4. 检查所有受限项是否仍标为 `RESTRICTED`、`NOT_EXECUTED`、
   `L2_REQUIRED` 或 `LIMITED_PASS`。
5. 检查报告是否出现不应存在的 `OFFICIAL_PASS`、第三方入网结论或官方 Verdict。
6. 检查仓库中是否提交了密码、token、私钥或真实用户隐私数据；标准原文只允许
   在经授权的私有组织内部交接，不应公开或转发到组织外部。
7. 将不一致、缺证据和无法复现的项目单独列出，不应静默修正。

## 4. 建议的复跑报告结论格式

同事应给出以下四类结论，而不是只写“通过”：

```text
仓库可复现性：PASS / FAIL
标准映射一致性：PASS / PARTIAL / FAIL
本地证据可信度：PASS / PARTIAL / FAIL
官方一致性：NO_OFFICIAL_VERDICT
发现的问题：
不能复现或不能核对的项目：
复跑用 commit：
复跑命令与报告路径：
```

## 6. 当前固定复跑入口

本文件对应的当前提交以 GitHub `main` 的最新 commit 为准，但复跑时必须使用
明确的 full hash，不能用“最新”作为可变目标。TC-011 的已知边界是：

- 本地 L1 行为证据通过；
- IPsec 为端口、SPI、Security Header 仿真，没有真实 Linux `xfrm`、ESP/AH；
- 没有真实 DUT/SS、eNB/EPC/IMS、USIM/ISIM 和无线接口；
- `official_verdict=null`；
- 正式判定仍需要合格 SS 或检测机构。
