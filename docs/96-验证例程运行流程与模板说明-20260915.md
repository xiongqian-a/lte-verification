# 验证例程运行流程与模板说明（2026-09-15）

> 一句话结论：整库通过 `run_official_suite.py` 一键运行；单条用例通过对应 checker 或证据脚本运行；34 条标准套件已经形成统一 Markdown 结构。此前模板由正式套件文件承载，现在已额外落盘为 `_templates/TC-TEMPLATE.md`，方便新增用例时直接复制。

## 1. 先区分“跑什么”

当前有四类运行对象，不能混成一件事：

| 层级 | 运行对象 | 产物 | 结论边界 |
|---|---|---|---|
| L0 标准骨架 | 34 条套件文档、registry、官方正文锚、验证流程、TP 判据 | 标准映射和验收判据 | 证明“标准怎么测”，不证明“被测栈已通过” |
| L1 checker 自检 | 23 个判定脚本的正负控夹具 | `SELFCHECK_PASS` | 证明脚本能执行、正负路径能触发 |
| L1 本地证据 | 本地日志、代码单测、模拟 IMS、测试台抓包 | `LOCAL_PASS` / `LIMITED_PASS` / `EXPECTED_FAIL` | 证明本地行为符合脚本判据，不是官方一致性 |
| L2 官方执行 | 合格 SS、仪表或检测机构按官方 TP 执行 | `OFFICIAL_PASS` / `OFFICIAL_FAIL` | 只有这一层能产生正式 36.523-1 / 34.229-1 Verdict |

## 2. 整库运行流程

### 2.1 一键命令

在发布仓库根目录运行：

```powershell
cd C:\标准例程-github
python -X utf8 run_official_suite.py
```

Windows 也可以运行：

```powershell
.\run.ps1
```

只检查标准和脚本、不重放本地日志时：

```powershell
python -X utf8 run_official_suite.py --skip-evidence
```

成功结束标志：

```text
UNIFIED RUNNER RESULT: OK
```

### 2.2 runner 实际执行的 11 个阶段

| 顺序 | 阶段 | 作用 |
|---:|---|---|
| 1 | `build_official_library.py` | 从 registry 和套件文档生成机器可读 official TP library |
| 2 | `verify_official_suite_metadata.py` | 校验套件元数据与官方 registry 一致 |
| 3 | `gen_detailed_progress.py` | 重建逐 TC 详细进度表 |
| 4 | `run_official_suite_checks.py` | 检查 34 条套件文档必需章节是否齐备 |
| 5 | `run_tc_selfchecks.py` | 执行 23 个判定脚本正负控自检 |
| 6 | `run_tc_evidence.py` | 重放已固化的 22 条本地真实证据 |
| 7 | `l1_skeleton_026_031.py` | 校验 TC-026~031 官方边界与受保护骨架 |
| 8 | `build_tc026_031_evidence_schema.py` | 生成官方章节、消息检查点和 TP Verdict 的机器可读 Schema |
| 9 | `run_l1_evidence_adapter_026_031.py` | 读取可选 L2 manifest；无合格证据时保持 `NOT_EXECUTED` |
| 10 | `verify_l1_evidence_adapter_026_031.py` | 校验 L2 适配器不会把本地证据升级成官方结论 |
| 11 | `report_factory.py` | 生成官方风格状态报告，但报告明确不是正式一致性证书 |

主要输出在 `generated/`：

- `84-本地证据复跑矩阵-20260914.md`
- `85-验证例程全量自检状态-20260914.md`
- `86-TC026-031-证据Schema与L1适配器-20260914.md`
- `92-验证例程详细进度总表-20260915.md`
- `official_report.md`

### 2.3 数据流

```text
官方规范正文
  -> registry/official_tp_registry.json
  -> suites/official_tp_suites/TC-xxx.md
  -> registry/official_tp_library.json
  -> runners/checker + evidence replay
  -> generated/ progress + audit + report
  -> L2 evidence manifest
  -> qualified SS / laboratory verdict
```

`registry` 管官方映射，套件文档管测试过程和判据，checker 管本地执行，generated 目录管本轮产物。任何一层缺失都必须显式标成 `RESTRICTED`、`NOT_EXECUTED` 或 `L2_REQUIRED`。

## 3. 单条用例怎么跑

### 3.1 先看套件文档

例如 TC-011：

```powershell
Get-Content -LiteralPath 'suites\official_tp_suites\TC-011-IMS初始注册.md'
```

文档第 8 节给出该用例自己的执行命令。常用命令包括：

```powershell
python runners/tc011_register_flow.py
python runners/tc012_mo_call.py
python runners/tc013_invalid_auth.py --selfcheck
python runners/tc014_rereg.py --raw --log <log-path>
python runners/tc015_restoration.py --log <log-path>
python runners/tc019_mt_call.py
python runners/tc020_hold_retrieve.py
python runners/tc021_conference_refer.py
python runners/tc022_audio_media.py
python runners/tc023_sdp_negotiation.py
python runners/tc025_vad_dtx.py
python runners/tc032_error_codes.py
python runners/tc033_timer_timeout.py
```

部分 checker 需要传入真实日志、抓包或测试床输出；套件文档里的命令参数是准入口。

### 3.2 只跑全部本地证据

```powershell
python runners/run_tc_evidence.py
```

该命令只复跑仓库中已固化的证据，不会访问仪表，也不会生成 `OFFICIAL_PASS`。

### 3.3 只跑脚本自检

```powershell
python runners/run_tc_selfchecks.py
```

该命令检查 checker 是否可执行以及正负控是否能触发。它不检查真实产品，也不出协议一致性结论。

## 4. 验证例程有模板吗

有。现在分为三层模板：

| 模板 | 路径 | 用途 |
|---|---|---|
| TC Markdown 模板 | `suites/official_tp_suites/_templates/TC-TEMPLATE.md` | 新建一条标准套件文档 |
| Registry 条目模板 | `registry/official_tp_registry.json` 中任一现有 entry | 登记官方规范、章节、映射等级、证据层级和 blocker |
| L2 证据模板 | `suites/official_tp_suites/_evidence/TC-026-031-evidence-manifest.template.json` | 回填合格 SS/实验室证据并按 TP Verdict 判 P/F |

### 4.1 TC Markdown 模板结构

统一要求包含：

```text
0. 元数据
0. 执行卡
1. 目的 / 为什么
2. 官方骨架
3. 前置条件
4. 验证流程
5. TP Verdict 判据
6. 当前本地证据
7. 受限 / L2_REQUIRED
8. 执行命令
```

执行卡固定回答八个问题：

```text
【用例ID】
【来源】
【测试目的】
【优先级】
【前置条件/SS环境】
【测试步骤】
【预期判据（逐消息检查）】
【通过标准】
【失败处理】
```

正文下方必须继续给出官方 TP 原文锚点、`.3.2` 步骤、`.3.3`/Annex 消息内容、本地证据和 L2 受限项。只说“参考某规范”但不给章节、行号、消息和判据，不满足当前模板要求。

## 5. 新增一条 TC 的标准动作

1. 复制 `_templates/TC-TEMPLATE.md`，命名成正式套件文件，例如 `TC-035-用例名称.md`。
2. 在 `registry/official_tp_registry.json` 增加同编号 entry，填写官方规范和章节。
3. 把官方正文锚点、测试目的、方法、Expected Sequence、Specific Message Contents 和 Test Requirements 填进模板。
4. 只有找到真实证据来源时才增加 checker；没有证据时保持 `STANDARD_ALIGNED` 或 `RESTRICTED`。
5. 给 checker 增加正控和负控 fixture，并纳 入 `run_tc_selfchecks.py`。
6. 给本地日志、抓包或代码证据建立稳定 artifact 路径，并纳入 `run_tc_evidence.py` 的证据矩阵。
7. 运行 `python -X utf8 run_official_suite.py`，确认 registry、套件、checker、证据和报告一致。
8. 正式送测时回填 L2 manifest；只有合格 SS/实验室能写 `OFFICIAL_PASS` 或 `OFFICIAL_FAIL`。

## 6. 结果词的含义

| 结果 | 含义 | 能不能作为官方一致性 PASS |
|---|---|---|
| `SELFCHECK_PASS` | 脚本和正负控夹具正常 | 不能 |
| `LOCAL_PASS` | 本地真实日志或行为满足 checker 判据 | 不能 |
| `LIMITED_PASS` | 核心本地行为通过，但标准要求仍有缺口 | 不能 |
| `EXPECTED_FAIL` | 负控应按设计失败，用于验证 checker 能识别问题 | 不能 |
| `STANDARD_ALIGNED` | 官方测试过程已对齐，尚未执行 | 不能 |
| `RESTRICTED` | 缺环境、设备、仪表或外部标准 | 不能，且不能写成失败 |
| `NOT_EXECUTED` | 没有可接受的官方 L2 证据 | 不能 |
| `OFFICIAL_PASS / OFFICIAL_FAIL` | 合格 SS/实验室按官方 TP 给出的 Verdict | 可以 |

## 7. 当前真实运行口径

- 统一 runner 可以一键执行并输出 `UNIFIED RUNNER RESULT: OK`。
- 34 条套件文档齐备，32 条有正文行号锚，28 条达到 `exact_line_ref`。
- 本地证据复跑条目 22 条：PASS 或 LIMITED_PASS 21 条，EXPECTED_FAIL 1 条，非预期 FAIL 0 条。
- checker 自检 23/23 PASS。
- TC-026~031 的 L2 结构已经搭好，当前 11 个章节均为 `NOT_EXECUTED`。
- 官方一致性 PASS 当前为 0，第三方入网 PASS 当前为 0。

这不矛盾：runner 的 `OK` 表示“仓库校验和本地证据复跑链路正常”，不表示“官方一致性测试通过”。
