# 下午汇报稿：自研协议栈前置验收例程

> 适用场景：向项目负责人、研发负责人汇报当前工作成果、边界和下一步安排。
>
> 汇报原则：不逐条讲 34 个用例；重点讲清楚“为什么做、做到什么程度、现在能承诺什么、还缺什么资源”。

## 一、开场直接结论

今天我不逐条展开 34 个测试用例，重点汇报三件事：

第一，我们已经把后续自研协议栈需要使用的验收例程搭起来了，覆盖 8 个模块、34 条功能 TC。

第二，这些例程已经尽量对齐 3GPP 官方规范和官方 TP 骨架，建立了机器可读映射、统一 runner 和本地证据入口。

第三，当前成果可以作为自研协议栈启动前的验收基线，但它还不是官方一致性测试结论。本地 PASS 不等于 36.523-1 或 34.229-1 官方一致性，也不等于第三方入网已经通过。这条边界我们会一直保留，不会把本地结果包装成官方 PASS。

一句话总结：

> 当前阶段交付的不是“官方一致性已经通过”，而是一套可以冻结、可以追溯、可以复跑、后续可以接入一致性仪表和检测机构的验收尺子。

## 二、为什么现在要做这件事

后续自研协议栈如果没有一套稳定的验收标准，会出现三个问题：

1. 开发做完以后再补测试标准，容易反复返工。
2. 功能测试用例、官方一致性用例和运营商入网用例混在一起，后面送审时对不上编号和判据。
3. 本地脚本 PASS 容易被误解成官方一致性 PASS，最后给项目传递错误结论。

所以这次工作的核心目标不是“先把 34 条都写成 PASS”，而是先把三件事钉住：

- 每条用例验证什么；
- 对应哪份规范、哪个章节、哪个官方 TP 判据；
- 当前证据属于本地验证、模拟环境，还是正式的一致性仪表执行。

这样等自研协议栈开始开发后，所有团队使用的是同一把尺子。

## 三、目前已经完成的工作

当前已经形成一套三层验收基线。

### L0：官方 TP 骨架

- 34 条标准套件文档已经齐备，覆盖模块 1 到模块 8。
- 每条文档都包含验证目的、前置条件、验证流程、官方依据、判据、当前证据和受限说明。
- 32 条已经有官方规范正文行号锚。
- 28 条达到 `exact_line_ref`，可以回到具体规范正文位置。
- 其余条目按 `partial`、`behavior` 或外部依赖如实标注，没有强行冒充官方独立一致性用例。

### L1：本地可执行验证框架

- 已建立机器可读注册表和用例库。
- 已建立统一 runner，可以一键执行套件生成、元数据校验、脚本自检、本地证据复跑、行号核验和报告生成。
- 当前本地证据复跑 22 条：
  - `PASS` 19 条；
  - `LIMITED_PASS` 2 条；
  - `EXPECTED_FAIL` 1 条，属于预期负控；
  - 非预期 `FAIL` 为 0。
- 23 个判定脚本自检全部通过。

这里需要说明：脚本自检通过，只证明脚本可执行、正负控路径可触发，不代表产品已经通过官方一致性。

### L2：真实一致性执行接口

- 已经为后续一致性仪表或检测机构预留证据接口。
- TC-026 到 TC-031 已结构化 11 个官方章节、114 个消息检查点、22 个 TP Verdict 和 77 个 Specific Message Contents 表。
- 这些章节当前全部是 `NOT_EXECUTED`，因为没有真实 SS、eNB/EPC、IMS System Simulator 或一致性仪表。
- 当前官方一致性 PASS 为 0，第三方入网 PASS 也为 0。

这不是测试失败，而是没有合格环境，不能输出正式结论。

## 四、当前结果应该怎么理解

建议用下面这张表向领导解释：

| 层级 | 当前成果 | 能不能作为最终结论 |
|---|---|---|
| L0 标准与官方 TP 骨架 | 34 条套件，32 条正文锚，28 条精确映射 | 可以作为验收标准基线 |
| L1 本地可执行证据 | 22 条证据复跑，21 条 PASS/LIMITED_PASS，非预期 FAIL 为 0 | 只能证明本地研发行为符合预期 |
| L2 官方一致性 | 尚未执行，`OFFICIAL_PASS=0` | 必须由一致性仪表或检测机构判定 |

所以当前状态可以这样表述：

- 自研启动：可以。
- 本地回归：可以复跑。
- 官方一致性：未执行，不能声称通过。
- 第三方入网：未执行，不能声称通过。
- 证据真实性：缺项、受限项和预期失败均如实保留。

## 五、当前主要受限项

当前受限项不是简单说“环境不够”，而是已经拆到了具体依赖。

1. 缺真实 eNB、EPC、SS 和 IMS System Simulator，相关 EPS、IMS 和端到端用例只能保留为 `RESTRICTED`。
2. TC-013 缺真实 HSS/IMS 侧无效 AKA 挑战注入，现有负控不能替代官方无效认证流程。
3. TC-025 的完整 AMR/EVS SCR、SID_FIRST、SID_UPDATE 时序还没有满足，当前只能按 `LIMITED_PASS` 处理。
4. TC-026 到 TC-031 缺 SRVCC、aSRVCC、SSAC、SCM、紧急 IMS、eCall、MSD、SLR 和 PSAP 的 L2 环境。
5. TC-034 缺具体 YD/T 编号和运营商 VoLTE 入库清单，不能编造编号或判据。
6. 正式一致性 PASS 必须来自 R&S、Anritsu、Keysight 或认可检测机构的 System Simulator，本地模拟和 OpenIMSCore 不能替代。

## 六、这套工作对项目的价值

这次工作的价值不是“多写了 34 条文档”，而是把后续开发和送审的路径固定下来：

- 自研协议栈开发前，验收标准已经确定；
- 每条实现差异可以回溯到规范、章节、正文行号和证据文件；
- 每轮开发提交可以先跑 L0/L1，及时发现回归；
- 后续取得仪表或检测机构资源后，可以直接把同一批 TC 接入 L2；
- 不需要重新设计一套验收标准，也不会因为本地 PASS 和官方 PASS 混用导致误判。

对项目的直接收益是：减少后期返工，提前暴露缺口，降低正式入网阶段的不可控风险。

## 七、下一步安排

下一步分三段推进。

### 第一段：冻结当前验收基线

把当前 34 条标准套件、机器可读映射、统一 runner 和证据报告作为第一版基线冻结。

冻结的含义不是“不能再改”，而是后续开发以这一版为起点，任何修改都要有规范依据、变更记录和证据更新。

### 第二段：支持自研协议栈开发

自研开始后，每轮提交执行统一 runner，持续检查：

- 标准套件有没有被破坏；
- 官方映射有没有失效；
- 本地证据有没有回归；
- 受限项有没有被误标成 PASS。

开发过程中能本地验证的继续做，缺少真实网络和仪表的部分继续保持受限，不伪造最终结论。

### 第三段：进入 L2 正式测试

取得合格环境和测试资源后，按官方 TP 执行：

1. 由一致性 SS 或仪表控制 UE，执行 36.523-1、34.229-1 等官方案例；
2. 由 IMS System Simulator 或检测机构执行 IMS、媒体和补充业务；
3. 根据具体运营商清单执行 YD/T 和 VoLTE 入库测试；
4. 由合格测试系统输出正式 `OFFICIAL_PASS / FAIL`。

## 八、需要公司支持的事项

为了让后续工作从“验收基线”走到“正式一致性”，需要三类资源：

1. L2 测试资源：R&S、Anritsu、Keysight 或认可检测机构的一致性测试能力。
2. 真实网络资源：eNB、EPC、IMS System Simulator，以及 SRVCC、SSAC、紧急呼叫和 eCall 所需测试台。
3. 入网输入：具体 YD/T 标准编号、运营商 VoLTE 入库规范、终端白皮书和测试清单。

当前没有这些资源并不影响自研启动和 L0/L1 回归，但会影响正式结论的产出时间。越早确定 L2 资源，后续送审排期越可控。

## 十、现场追问简答

### 问：现在 34 条是不是都已经通过了？

答：不能说全部通过。34 条标准套件文档已经齐备，本地有 22 条证据复跑，其中 21 条 PASS 或 LIMITED_PASS。官方一致性 PASS 目前是 0，因为还没有一致性仪表和合格 SS。

### 问：为什么不能直接说本地 PASS 就是通过？

答：本地脚本只能判断日志、报文、字段或行为是否符合我们写的断言。官方一致性要求由合格 System Simulator 按官方 TP 控制测试流程并给出 Verdict，两者不是一回事。

### 问：现在可以开始自研吗？

答：可以。现在冻结的是验收基线、官方映射、执行框架和证据入口，不依赖自研先完成。自研完成后直接按同一套 TC 和规范进行回归和 L2 测试。

### 问：为什么不一开始就做官方测试？

答：官方测试需要一致性仪表、ISS 和真实网络。当前没有这些资源，但标准套件、官方 TP 映射、本地执行框架和 L2 接口可以先完成。这样资源到位后不用重新搭验收标准。

### 问：为什么还有 RESTRICTED 和 NOT_EXECUTED？

答：因为这些项目缺真实环境或外部输入，例如 SRVCC、SSAC、eCall、无效 AKA 挑战、YD/T 和运营商清单。不能把缺证据的项目标成 PASS。

### 问：当前最大的风险是什么？

答：最大风险不是本地脚本失败，而是后续把本地 PASS 误当成官方一致性，或者没有提前准备 L2 测试资源，导致送审时间不可控。

### 问：这套东西最终怎么用于第三方入网？

答：内部 TC 编号用于开发追溯，官方 TC 编号和 TP Verdict 作为骨架。L2 阶段由合格仪表或检测机构执行，输出正式 P/F。运营商部分再叠加 YD/T 和入库清单。

## 十一、汇报时不能说的话

- 不能说“36.523-1 一致性已经通过”。
- 不能说“34.229-1 IMS 一致性已经通过”。
- 不能说“本地脚本 PASS 等于 pjsua 新栈合规”。
- 不能说“模拟 IMS 等于 IMS System Simulator”。
- 不能说“第三方入网已经通过”。
- 不能把 `NOT_EXECUTED`、`RESTRICTED` 或 `EXPECTED_FAIL` 描述成 PASS。

## 十二、汇报时可以明确承诺的事

- 可以冻结本版验收尺子，作为自研协议栈的固定回归基线。
- 可以按同一批 TC 先跑 L0/L1 本地证据，再进入 L2 仪表或检测机构。
- 可以在取得合格环境后接入现有证据适配器。
- 可以把每个差异回溯到具名规范、章节、正文行号和原始证据文件。
- 不会修改内部 TC 编号掩盖实现差异，也不会伪造官方 PASS。
