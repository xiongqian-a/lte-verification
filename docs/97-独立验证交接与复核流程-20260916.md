# 独立验证交接与复核流程

> 目的：让另一个没有当前会话记忆的 agent，在不知道既有结论的情况下，
> 从固定 commit 独立复跑并审查验证套件。
>
> 边界：独立复核可以验证仓库可复现性、标准映射、脚本判据和证据来源；
> 没有合格 SS、仪表或检测机构时，仍然不能产生官方一致性 Verdict。

## 1. 先准备什么

交给另一个 agent 的材料必须包括：

1. GitHub 仓库和固定的 full commit hash，不使用“main 最新”作为复核目标。
2. 干净的独立 checkout，不复用当前工作区、不读取当前会话结论。
3. Python 3.10+ 和 Git。
4. 本仓库不随包分发的规范原文件，至少按 `registry/official_tp_registry.json`
   的 `sources` 字段提供对应版本 PDF/DOC/DOCX。
5. 明确复核边界：本地 `PASS` 不能写成 `OFFICIAL_PASS`。
6. 一个独立输出目录，例如 `outputs/independent-verification`。

不要把“我已经跑过且全部通过”当作复核输入。只给仓库、commit、规范原文、
执行入口和验收边界。

## 2. 最短执行方式

在全新目录克隆：

```powershell
git clone https://github.com/xiongqian-a/lte-verification.git C:\verify-lte
cd C:\verify-lte
git checkout <full-commit-hash>
```

先确认 checkout：

```powershell
git status --short --branch
git rev-parse HEAD
git remote -v
```

运行独立复核入口：

```powershell
python -X utf8 runners/independent_verification.py `
  --expected-commit <full-commit-hash> `
  --out-dir outputs/independent-verification
```

复核报告和机器可读结果会写到：

```text
outputs/independent-verification/independent-verification-<timestamp>.md
outputs/independent-verification/independent-verification-<timestamp>.json
```

脚本会执行：

- 统一 runner；
- registry 与 34 条套件元数据一致性；
- 全部 checker 自检；
- 已固化本地证据复跑；
- TC-011 注册流自检；
- TC-011 L1 IPsec/SUBSCRIBE/NOTIFY 自检；
- TC-011 必须保持 `LIMITED_PASS / L1_LOCAL_SIMULATED`、`official_verdict=null`；
- 关键 artifact SHA256；
- 运行前后 Git 状态和 diff stat。

成功输出必须包含：

```text
INDEPENDENT VERIFICATION: PASS
TC011_INVARIANTS: PASS
OFFICIAL_VERDICT: null
```

该 `PASS` 是“独立复跑和内部一致性检查通过”，不是协议一致性结论。

## 3. 另一个 agent 还必须人工检查什么

自动化脚本只能覆盖仓库内部一致性，不能替代标准审查。独立 agent 必须继续做：

1. 对照规范原文抽查 registry 和 TC 文档中的 clause、line anchor、消息字段、
   前置条件和 TP Verdict。
2. 检查 checker 的正控、负控和合成 fixture，确认不是“脚本生成输出后再由
   同一脚本给自己判 PASS”。
3. 对每条本地证据追溯原始日志、抓包或测试台输出，确认输入不是临时伪造。
4. 检查所有受限项是否仍标为 `RESTRICTED`、`NOT_EXECUTED`、
   `L2_REQUIRED` 或 `LIMITED_PASS`。
5. 检查报告是否出现不应存在的 `OFFICIAL_PASS`、第三方入网结论或官方 Verdict。
6. 检查仓库中是否提交了密码、token、私钥、真实用户隐私数据或未授权规范全文。
7. 将不一致、缺证据和无法复核的项目单独列出，不应静默修正。

## 4. 建议的复核报告结论格式

独立 agent 应给出以下四类结论，而不是只写“通过”：

```text
仓库可复现性：PASS / FAIL
标准映射一致性：PASS / PARTIAL / FAIL
本地证据可信度：PASS / PARTIAL / FAIL
官方一致性：NO_OFFICIAL_VERDICT
发现的问题：
不能复核的项目：
复核用 commit：
复核命令与报告路径：
```

## 5. 可直接发给另一个 agent 的提示词

```text
你是独立验证 Agent。不要沿用任何之前的会话结论，只把仓库文件、固定 commit
和规范原文当作证据。

仓库：https://github.com/xiongqian-a/lte-verification
固定 commit：<填写 full commit hash>
规范原文：按 registry/official_tp_registry.json 的 sources 字段核对
工作目录：新建一个独立目录，不修改原工作区

任务：
1. clone 仓库并 checkout 指定 full commit。
2. 先报告 HEAD、分支、远端、工作树状态。
3. 运行：
   python -X utf8 runners/independent_verification.py --expected-commit <commit> --out-dir outputs/independent-verification
4. 阅读生成的 Markdown/JSON 报告，但不要只相信报告。逐项检查：
   - registry 与套件文档是否一致；
   - 官方 clause、line anchor、消息字段和 TP Verdict 是否能由规范原文支持；
   - checker 是否有有效正控和负控，是否存在自证式 fixture；
   - 本地证据是否可追溯到真实日志、抓包或测试台输出；
   - TC-011 是否仍为 LIMITED_PASS / L1_LOCAL_SIMULATED 且 official_verdict=null；
   - 是否错误地把本地结果升级为 36.523-1、34.229-1 或第三方入网 PASS。
5. 不修复问题，不代替我改结论。把所有冲突、缺证据和无法复核项列出来。

最终按以下格式回复：
仓库可复现性：
标准映射一致性：
本地证据可信度：
官方一致性：NO_OFFICIAL_VERDICT
发现的问题：
不能复核的项目：
复核用 commit：
复核命令与报告路径：
```

## 6. 当前固定复核入口

本文件对应的当前提交以 GitHub `main` 的最新 commit 为准，但复核时必须使用
明确的 full hash，不能用“最新”作为可变目标。TC-011 的已知边界是：

- 本地 L1 行为证据通过；
- IPsec 为端口、SPI、Security Header 仿真，没有真实 Linux `xfrm`、ESP/AH；
- 没有真实 DUT/SS、eNB/EPC/IMS、USIM/ISIM 和无线接口；
- `official_verdict=null`；
- 正式判定仍需要合格 SS 或检测机构。
