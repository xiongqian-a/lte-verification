## 1. 项目背景

### 1.1 为什么不能只写“字段符合预期”的脚本

LTE/IMS 协议栈涉及 UE、RAN、EPC、IMS、USIM/ISIM、媒体和补充业务。单看
一条日志“有没有 REGISTER”或“有没有 INVITE”不足以证明协议实现可靠，原因
包括：

1. 官方用例规定了严格的前置状态、消息顺序、字段、定时器、容差和允许变体；
2. 同一种业务可能经过多个标准，例如 IMS 呼叫同时涉及 34.229-1、24.229、
   26.114 和相关补充业务规范；
3. 本地模拟、真实测试床、合格 SS、仪表和检测机构实验室的证明力不同；
4. 后续自研协议栈会持续修改，如果没有稳定的验收入口，每次修改都很难判断
   是否发生回归；
5. 测试结果必须能追溯到具名规范、章节、步骤和证据来源，否则送审时很难解释。

因此本项目采用“三层实现”：

```text
L0  官方 TP 骨架
    -> 规范、章节、前置、过程、判据、Annex、消息内容和边界

L1  可执行测试框架
    -> 日志解析、抓包、单测、模拟器、响应器和本地测试床

L2  真实一致性执行环境
    -> 合格 SS / 仪表 / 检测机构按官方 TP 执行并输出官方 Verdict
```

### 1.2 本阶段的产品化目标

后续自研协议栈开发出来后，可以直接复用同一套标准骨架和检查入口：

1. 用 L0 确认测试目标没有偏离正式标准；
2. 用 L1 对新代码产生的真实日志做快速回归；
3. 把遗留问题按 `RESTRICTED`、`NOT_EXECUTED`、`L2_PENDING` 保留；
4. 到正式阶段再把同一套步骤和判据交给合格 SS、仪表或实验室；
5. 最终只有 L2 的输出才能写成官方一致性 PASS/FAIL。

## 2. LTE、EPC 和 IMS 基础

### 2.1 端到端网络角色

| 角色 | 作用 |
|---|---|
| UE | 终端和协议栈主体，包含 NAS、RRC、SIP、SDP、RTP 等能力 |
| eNB | LTE 无线接入，负责 RRC、无线承载、调度和 NAS 消息透传 |
| MME | EPS 移动性管理、附着、TAU、Service Request、承载控制 |
| SGW/PGW | 传统 EPC 用户面锚点和 PDN 连接；5G 体系中对应 SMF/UPF 等功能 |
| HSS | 用户签约、鉴权向量和移动性数据 |
| P-CSCF | IMS 入口代理，处理 REGISTER、INVITE 和安全关联 |
| I-CSCF | IMS 入口查询和 S-CSCF 选择 |
| S-CSCF | IMS 注册、业务触发和服务路由 |
| IMS HSS | IMS 用户身份、服务配置和鉴权数据 |
| 媒体端 | RTP/RTCP、AMR/AMR-WB/EVS、VAD/DTX、抖动和丢包处理 |

### 2.2 EPS 承载模型

EPS 中业务不是简单地“发一个 IP 包”，而是通过 PDN、默认承载和专用承载承载：

- `APN/DNN`：选择业务网络，例如普通互联网和 IMS 通常使用不同 APN；
- `PDN Connection`：UE 到某个 PDN 的逻辑连接；
- `Default EPS Bearer`：建立 PDN 时的默认承载；
- `Dedicated EPS Bearer`：为特定 QoS/TFT 业务建立的专用承载；
- `EBI`：EPS Bearer Identity，用于关联请求、接受、释放和 TFT；
- `TFT`：Traffic Flow Template，决定上行 IP 包走哪个承载；
- `QCI/5QI`：QoS 等级，IMS 信令和语音通常有不同 QoS 要求；
- `PTI`：Procedure Transaction Identity，关联 ESM 请求和响应。

关键状态：

```text
UE: EMM-DEREGISTERED / EMM-REGISTERED
UE: EMM-IDLE / EMM-CONNECTED
ESM: BEARER CONTEXT INACTIVE / ACTIVE
ESM: PROCEDURE TRANSACTION INACTIVE / ACTIVE / PENDING
```

### 2.3 典型 EPS 流程

```text
UE -> eNB -> MME: ATTACH REQUEST
MME <-> HSS: 鉴权和签约查询
MME -> UE: ATTACH ACCEPT
MME -> UE: ACTIVATE DEFAULT EPS BEARER CONTEXT REQUEST
UE -> MME: ACTIVATE DEFAULT EPS BEARER CONTEXT ACCEPT
UE -> MME: PDN CONNECTIVITY REQUEST / SERVICE REQUEST / TAU REQUEST
```

### 2.4 IMS 和 SIP

IMS 的主要协议是 SIP。初始注册通常包含：

```text
UE -> P-CSCF: REGISTER
P-CSCF -> UE: 401 Unauthorized + WWW-Authenticate
UE -> P-CSCF: REGISTER + Authorization response
P-CSCF -> UE: 200 OK + Service-Route + P-Associated-URI
UE -> P-CSCF: SUBSCRIBE reg
P-CSCF -> UE: NOTIFY reginfo
UE -> P-CSCF: NOTIFY 200 OK
```

IMS AKA 的核心目的，是让 UE 和网络基于 USIM/ISIM 的共享密钥完成双向鉴权，
并防止 MAC、SQN、nonce 和 AUTS 处理被错误简化。

### 2.5 SDP、RTP、RTCP 和媒体

- `SDP` 协商媒体类型、端口、协议、编解码和带宽；
- `RTP` 承载编码后的媒体包；
- `RTCP` 提供统计、报告和质量反馈；
- `AMR/AMR-WB` 使用 ToC 字段表示 speech、SID、NO_DATA 等帧类型；
- `VAD` 判断语音/静音，`DTX` 在静音期减少或停止发送；
- `SID/CN` 用于舒适噪声更新；
- 官方媒体判定不能只靠“RTP 有包”或“能听清”，还要核对 SDP、RTP 时间戳、
  帧类型、周期、同步、抖动、丢包和允许变体。

## 3. 标准体系和职责分工

本仓库使用的标准不是一个孤立文件，而是一个分工体系：

| 标准 | 在本项目中的职责 |
|---|---|
| TS 36.523-1 | LTE/E-UTRA UE 一致性测试主骨架，覆盖 RRC、NAS、承载、移动性、SRVCC、接入控制和紧急/eCall 等 |
| TS 34.229-1 | IMS UE 一致性测试主骨架，覆盖注册、呼叫、保持、会议、REFER、错误码和定时器 |
| TS 24.229 | IMS UE 的 SIP/IMS 协议行为和过程 |
| TS 24.301 | EPS NAS 状态机、PDN、承载、ESM cause 和定时器 |
| TS 24.628 | 补充业务和 REFER/会议相关行为 |
| TS 24.173 | MMTel 补充业务，例如 hold、conference、ECT |
| TS 26.114 | MTSI 媒体、SDP、RTP/RTCP、带宽和媒体性能要求 |
| TS 26.093 | AMR 自适应多速率和 source controlled rate |
| TS 26.193 | AMR 终端性能要求 |
| TS 26.450 / 26.451 | EVS DTX/VAD 相关行为和测试要求 |
| TS 36.508 | 测试环境、默认配置、通用消息表、参考承载和初始条件 |
| TS 36.509 | 测试环回和测试控制过程 |
| TS 34.108 | 通用 UE 测试环境和参考配置 |
| RFC 3261 | SIP 基础协议和事务/定时器 |
| RFC 3515 | SIP REFER |

### 3.1 为什么同一 TC 可能对应多个标准

例如 IMS MO 语音呼叫不是只看一条 INVITE：

1. `34.229-1` 定义 IMS UE 的官方 TP 过程和 Expected Sequence；
2. `24.229` 定义 SIP 消息和注册/呼叫状态处理；
3. `26.114` 定义 SDP/RTP/RTCP 和媒体要求；
4. `36.508` 提供测试环境、默认消息和参考承载；
5. 补充业务再引用 `24.173`、`24.628` 等。

因此映射表不能只写一个大规范名，至少要有：

```text
内部 TC ID
-> 官方规范
-> 官方章节/TP ID
-> .3.1 前置条件
-> .3.2 测试过程
-> .3.3 Expected Sequence / Specific Message Contents
-> .3.4 Verdict / Test Requirements
-> Annex 默认消息或补充流程
-> 本地 checker 和证据
-> L2 blocker
```

### 3.2 Release 和版本边界

规范版本不能随意混用。一个真实的处理例子是 `TS 34.229-1`：

- Release 14 的 IMS 正文主锚使用 `V14.7.0`；
- `V14.8.0` 已把测试要求指向 Release 15，并把部分正文和 Annex 标为 Void；
- 所以做条款和行号核对时，必须记录具体版本，不能只写“34.229-1”。

## 5. 逐条 TC 的验证方法

每条 TC 的交付流程是固定的：

1. **确定内部 TC 目标**：明确验证 UE 的什么行为、为什么需要验证。
2. **定位官方骨架**：找到官方 TP 或最接近的标准过程，记录版本和条款。
3. **展开官方步骤**：
   - `.3.1` 前置状态和环境；
   - `.3.2` 测试过程和 Expected Sequence；
   - `.3.3` Specific Message Contents；
   - `.3.4` Test Requirements 和 Verdict；
   - Annex 默认消息、配置表和允许变体。
4. **建立机器可读映射**：写入 registry 和套件文档。
5. **准备真实输入**：优先使用真实日志、抓包、测试床或模拟器输出。
6. **实现 checker**：把关键消息、字段、顺序、状态、定时器和边界转换成断言。
7. **增加正控和负控**：证明 checker 不会把空文件或错误报文误判成 PASS。
8. **标明证据层级**：`LOCAL_PASS`、`LIMITED_PASS`、`STANDARD_ALIGNED`、
   `RESTRICTED`、`NOT_EXECUTED` 或 `L2_PENDING`。
9. **接入 L2**：只有在获得合格 SS/仪表/实验室结果时才写官方 Verdict。

### 5.1 一条 TC 的最小执行卡

```text
【用例 ID】TC-xxx
【标准来源】规范名 + 版本 + 条款/TP ID
【测试目的】验证什么协议行为
【优先级】P0/P1/P2
【前置条件】UE、网络、IMS、用户、承载、定时器和测试台状态
【官方步骤】.3.1 -> .3.2 -> .3.3 -> .3.4
【允许变体】规范允许的替代编码、消息顺序和实现选择
【通过判据】消息、字段、状态、定时器、容差和 Verdict
【失败处理】保留日志、抓包、复现步骤和缺陷关联
【当前证据】本地、L1、L2 或未执行
【边界】缺什么环境或仪器，不能把什么写成 PASS
```

## 6. 关键案例复盘

### 6.1 TC-004：PDN REJECT、状态机、T3482 和 back-off

**目的**：验证 UE 收到 `PDN CONNECTIVITY REJECT` 后，不会错误地保持 ESM
过程激活状态；遇到扩展等待定时器时，能执行 back-off 而不是持续重试。

**标准来源**：

- `TS 36.523-1 10.5.3 / 10.5.4`；
- `TS 24.301 6.5.1.4`；
- ESM cause #32、`T3482`、`T3346` 和扩展等待定时器。

**验证流程**：

1. UE 发起 IMS APN 的 PDN 连接；
2. 网络返回带 PTI 和 ESM cause 的 REJECT；
3. 检查 UE 是否停止对应 ESM 事务并进入正确的非活动状态；
4. 在 RRC reject + Extended wait timer 场景中检查 back-off；
5. 到期前不得重新发起，超时后才允许重试。

**本地证据**：UE 侧 `nas_test` 复跑观察到 cause、状态、`T3482` 和 720 秒
back-off。  
**限制**：缺少真实核心网注入 REJECT 和实时等待定时器的 L2 Verdict。

这条案例适合在面试中说明：验证不是只查“字段值”，还要检查状态机和定时器。

### 6.2 TC-005：双 PDN 和 IMS 专用承载

**目的**：验证普通 PDN 与 IMS PDN 能共存，IMS 业务能建立第二默认承载和
关联专用承载。

**真实 L1 环境**：

- co1750 服务器；
- srsRAN 4G；
- 补丁版 Open5GS；
- UE、eNB、MME、SMF、UPF 日志和抓包。

**观察到的事实**：

```text
internet default bearer: EBI=5
ims second default bearer: EBI=6
ims dedicated bearer: EBI=7，linked_bearer_id=6
MME 保持两个 session
SGWC 完成 Create Bearer Response
```

**结论**：`LIMITED_PASS`。  
**原因**：IPv6/IPv4v6 分配、method II P-CSCF discovery 的逐字段检查、网络侧
additional PDN 释放/E1 结束态和官方 SS Verdict 仍受限。

这条案例适合展示：能把 UE 侧、eNB 侧和核心网侧日志串起来，而不是只看单一
脚本的返回码。

### 6.3 TC-011：IMS 初始注册、IPsec 和安全关联

**目的**：验证 UE 完成 IMS 初始注册，包括：

- 初始未保护 REGISTER；
- 401 和 AKAv1-MD5 challenge；
- 第二次 REGISTER 和 Authorization；
- `Security-Client` / `Security-Verify`；
- 端口、SPI 和受保护关联；
- `SUBSCRIBE` / `NOTIFY` registration event package；
- 两轮 PIXIT：`HMAC-MD5-96` 和 `HMAC-SHA-1-96`。

**官方骨架**：

- `TS 34.229-1 V14.7.0 Clause 8.1`；
- Annex C.2 Steps 4-11；
- Annex A.1.1 到 A.1.6 默认消息；
- `TS 24.229 C.2`；
- `TS 36.508 4.5A.6.3-1`。

**本地结果**：两轮 PIXIT 各 8/8 通过，输出 transcript、verdict 和 summary。  
**边界**：

- 当前 IPsec 是端口、SPI 和 Security Header 级仿真；
- 没有创建真实 Linux `xfrm state/policy`；
- 没有发送或校验真实 ESP/AH；
- 没有真实 UE/USIM/ISIM 和合格 SS；
- `official_verdict` 始终为 `null`。

这条案例是“如何完整实现一个协议用例框架”的最佳展示：它覆盖了消息、状态、
安全字段、多次注册、订阅通知和 PIXIT 参数，同时没有夸大官方一致性。

### 6.4 TC-013：无效 AKA challenge

**目的**：验证 UE 遇到 MAC 参数无效或 SQN 超范围时，不会错误地建立临时
安全关联，而是按标准返回重新同步或重新鉴权所需的材料。

**标准来源**：

- `TS 34.229-1 V14.7.0`；
- Invalid Behaviour：MAC Parameter Invalid / SQN out of range。

**当前做法**：实现本地判定引擎和正负控；真实 bad-key 日志被正确判为
`EXPECTED_FAIL`，说明日志不是官方无效挑战，不能误判。

**限制**：真实 IMS/HSS 注入错误鉴权向量，以及完整的 `AUTS`、同步失败和临时
SA 行为还没有 L2 证据。这个案例的价值在于“测试器不会为了跑绿而伪造 PASS”。

### 6.5 TC-022 / TC-023：音频媒体和 SDP

**目的**：

- 验证 SDP offer/answer 的编解码、方向和媒体属性；
- 验证 RTP 媒体流持续、端口、时间戳和基本统计；
- 把 `34.229-1` 的呼叫 TP 与 `26.114` 的媒体要求关联起来。

**已经完成**：本地 pjsua 日志、SDP 字段检查、RTP 解析和基本媒体证据。  
**尚未完成**：官方 SDP 子例级全量覆盖、媒体测量表、抖动/丢包/同步容差和
合格媒体仪表判定。

### 6.6 TC-025：VAD/DTX 与 SID，不把违例打包成 PASS

这是一个非常适合面试的项目案例，因为它体现了验证工程的专业性：

**真实抓包结果**：

```text
AMR speech ft=2: 218
SID ft=8: 4
NO_DATA ft=15: 10
SID interval: 1000 frames
expected SID_UPDATE interval: 8 frames
```

依据 `TS 26.093`：

- 正常语音 burst 后应有 hangover、`SID_FIRST` 和 `SID_UPDATE` 节奏；
- 20 ms 帧在 8000 Hz 时钟下是 160 ticks，8 帧应为 1280 ticks；
- `NO_DATA` 不应在接入网传输，但抓包里实际出现了 10 个；
- 观测到的 SID 间隔为 1000 帧，不符合 8 帧 cadence。

所以整体只能记录为：

```text
LOCAL_BEHAVIOR=PARTIAL
STANDARD_ASSERTION=FAIL
RESULT=LIMITED_PASS
OFFICIAL_VERDICT=null
```

这说明验证体系的职责不是“把结果跑成绿的”，而是让真实证据、标准判据和缺陷
结论保持一致。

## 7. 结果词和证据层级

| 结果 | 含义 | 可以怎么用 |
|---|---|---|
| `LOCAL_PASS` | 本地日志、报文或行为符合 checker 判据 | 开发回归和字段级证据 |
| `LIMITED_PASS` | 核心行为通过，但仍有变体、环境或官方字段未覆盖 | 局部可用，必须保留限制 |
| `SELFCHECK_PASS` | checker 自身和正负控可执行 | 只证明判定器可用 |
| `STANDARD_ALIGNED` | 已完成标准映射，但未完整执行 | 可用于后续送测准备 |
| `RESTRICTED` | 缺标准、网络、仪表、运营商或访问权限 | 既不是 PASS 也不是 FAIL |
| `NOT_EXECUTED` | 没有合格证据 | 不能用历史模拟冒充执行 |
| `OFFICIAL_PASS` / `OFFICIAL_FAIL` | 合格 SS 或认可实验室给出的 Verdict | 官方一致性结论 |

### 7.1 Golden replay 和 fresh-DUT 的区别

- **Golden replay**：对固定 commit 内已经提交的历史证据重新跑 checker，
  用来证明仓库快照可复现。
- **fresh-DUT**：针对新编译或修改后的协议栈，重新采集日志、抓包和消息，
  用来判断新代码是否满足相同判据。

两者不能混用。旧日志的 PASS 不能自动继承给新协议栈。

## 8. 工程实现和代码链路

### 8.1 为什么使用 Python 标准库

核心 runner 只依赖 Python 标准库，目的是让同事在 Windows、Linux 和服务器
上都能无额外安装直接复跑：

```powershell
git clone https://github.com/xiongqian-a/lte-verification.git
cd lte-verification
.\bootstrap.cmd --doctor
.\bootstrap.cmd --verify-standards
.\bootstrap.cmd
```

Linux/macOS：

```sh
./bootstrap.sh
```

### 8.2 统一 runner 的执行顺序

`run_official_suite.py` 依次完成：

1. 便携安装和机器路径检查；
2. 标准原文包的路径、字节数和 SHA256 校验；
3. 从 registry 和套房文档重建机器可读库；
4. 重建 `verification-architecture.html`；
5. 校验 TC 元数据和 registry 一致性；
6. 重建详细进度表；
7. 校验 34 份套件文档的必需章节；
8. 执行 checker 正控和负控；
9. 复跑仓库内的本地证据矩阵；
10. 校验 TC-026 到 TC-031 的官方证据 Schema；
11. 执行 L2 adapter 语义保护检查；
12. 生成报告，但不自动生成官方 Verdict。

### 8.3 架构页面

`verification-architecture.html` 是离线自包含页面，包含：

- 模块和 TC 图谱；
- 每条 TC 的输入、脚本、证据和输出；
- 官方映射和行号引用；
- 证据文件的查看入口；
- 服务器路径和 blocker；
- 本地结果与 L2 边界。

页面的作用是让复核者不需要读完全部 JSON，也能快速判断：

> 这条 TC 测什么、依据什么、用了什么输入、产出什么证据、现在缺什么。

### 8.4 CI

`.github/workflows/verify.yml` 在 Linux 和 Windows 上执行统一 runner，并在
运行后执行 `git diff --exit-code`，防止生成物漂移或隐式环境依赖进入仓库。

> 这个项目的背景是，自研 LTE/IMS 协议栈后续需要开发、回归和送测，但当时

> 映射到标准，例如 EPS 承载看 36.523-1 和 24.301，IMS 注册和呼叫看 34.229-1

> 测试结论可信。

### 9.4 面试官可能追问

**Q1：你实际写了什么？**

> 主要完成标准到 TC 的映射、suite 文档、registry、checker 和证据链，以及
> 统一 runner、报告、HTML 页面、bootstrap 和 CI。不是只整理文档，代码会
> 读取真实日志或抓包，运行正负控，生成可追踪结果。

**Q2：为什么只有 22 条左右能本地跑？**

> 因为“34 条功能索引”不等于“34 条都有实时环境”。有真实输入、官方骨架和
> checker 的才能产出 L1 证据；缺 eNB、EPC、IMS、媒体仪表或运营商标识的
> 条目必须保留受限状态。这样不会为了数量伪造结果。

**Q3：本地 PASS 和官方一致性差在哪里？**

> 本地 PASS 只证明输入日志符合 checker 派生判据。官方一致性由合格 SS
> 按官方 TP 控制消息、容差和 Verdict 规则判定，还需要正确的测试配置、
> PIXIT 和实验室环境。

**Q4：如果自研代码改了怎么办？**

> 复用 L0 标准骨架，重新采集 fresh-DUT 证据，不继承旧 Golden replay。
> 先跑 L1 快速回归，再按需进入 L2。

**Q5：你怎么防止误判？**

> 每个 checker 除了正控，还准备负控；例如 TC-025 的真实抓包出现 NO_DATA
> 和错误 SID cadence，系统没有强行判 PASS，而是记录 `STANDARD_ASSERTION=FAIL`
> 和 `LIMITED_PASS`。

**Q6：为什么需要 Annex？**

> 官方主体章节定义测试目的和过程，Annex 常常提供默认消息、测试配置、
> 补充流程或特殊场景。只看正文可能漏掉 Specific Message Contents 和允许变体。

**Q7：PIXIT 是什么？**

> 测试实现参数。像 IPsec 算法轮次、定时器、端口或其他可配置项，不同 PIXIT
> 可能要求同一 TP 分轮执行。TC-011 就分别跑了 HMAC-MD5-96 和
> HMAC-SHA-1-96。

### 9.5 不建议在面试中说的话

不要说：

- “我自己实现了 LTE/IMS 协议栈”；
- “34 条都过了”；
- “本地测试就是官方一致性”；
- “Open5GS 跑通就代表 UE 合规”；
- “抓到了 RTP 就完成了媒体一致性”；
- “等自研代码写完，旧日志可以直接证明它通过”；
- “没有仪表也能得出官方 Verdict”。

更稳妥的说法是：

- “我建立了验证基线，并跑通了可执行的本地层”；
- “我把官方 TP 转成了可追溯的结构和检查接口”；
- “本地证据用于回归，官方结论留给 L2”；
- “我保留并记录缺口，而不是伪造通过”。

## 10. 系统学习路线

### 10.1 第一轮：建立网络地图

1. 学 EPS 架构：UE、eNB、MME、SGW/PGW、HSS；
2. 学 PDN、APN、默认承载、专用承载、EBI、PTI 和 TFT；
3. 学 IMS 架构：P/I/S-CSCF、HSS、IMPI、IMPU、Service-Route；
4. 学 SIP 注册和呼叫基础流程；
5. 学 SDP、RTP、RTCP、AMR 和 EVS 的基本概念。

目标：看到一条日志时，能说出消息在哪一层、由谁发送、属于哪个状态机。

### 10.2 第二轮：按模块读标准

建议顺序：

1. `TS 36.508`：先理解测试环境和默认消息；
2. `TS 24.301`：NAS 和 ESM 状态机；
3. `TS 36.523-1`：LTE UE 官方 TP；
4. `TS 34.229-1`：IMS UE 官方 TP；
5. `TS 24.229`：SIP/IMS UE 行为；
6. `TS 26.114` 和 `TS 26.093/26.193`：媒体和 AMR；
7. `TS 24.173/24.628`：补充业务、hold、conference 和 REFER；
8. YD/T 和运营商 VoLTE 入库要求。

### 10.3 第三轮：沿一条案例走完整链路

建议选择 TC-011：

```text
标准 34.229-1 8.1 / Annex C.2 / Annex A
-> 注册消息和 401 挑战
-> AKA 和 Authorization
-> IPsec Security-Client / Security-Verify
-> 200 OK 和 Service-Route
-> SUBSCRIBE / NOTIFY
-> checker 和 transcript
-> L1 结果
-> 仍然缺失的 L2 条件
```

然后沿着同一方法复做 TC-004、TC-005、TC-022/023 和 TC-025。

### 10.4 第四轮：做一次 fresh-DUT

1. 记录完整 commit hash；
2. 修改一段自研协议栈代码；
3. 重新产生日志或抓包；
4. 用同一 checker 运行；
5. 对比旧 Golden replay 和新 fresh-DUT；
6. 如果字段或行为变化，检查是实现回归还是标准允许变体；
7. 保持 `OFFICIAL_VERDICT=null`，直到有合格 L2 证据。

## 12. 当前遗留项

1. `36.523-1` 和 `34.229-1` 官方一致性 Verdict：必须有合格 SS/仪表/实验室。
2. 真实 eNB/EPC：TC-002、TC-003、TC-006 到 TC-010 等多条缺少实时端到端。
3. 真实 IMS/呼叫台：MT、hold、conference、REFER、紧急和 eCall 仍缺完整对端。
4. 真实 IPsec：TC-011 还没有 Linux `xfrm`、ESP/AH 和真实 UE/SS。
5. 媒体仪表：TC-022 到 TC-025 缺官方测量表、抖动/丢包/同步和真实媒体性能判定。
6. 中国入网：TC-034 缺具体 YD/T 编号和运营商 VoLTE 入库清单。
7. 版本边界：后续新增标准时必须记录版本，不能把不同 Release 的正文混在一起。
8. fresh-DUT 流程：自研协议栈代码变化后必须重新采集证据，不能复用旧 PASS。
