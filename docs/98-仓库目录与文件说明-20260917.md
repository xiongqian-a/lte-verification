# 仓库目录与文件说明

> 目标：让第一次接手仓库的同事快速判断每个目录和文件的用途，尤其分清
> “测试用例”“执行脚本”“标准映射”“历史证据”“生成报告”和“本地运行产物”。
>
> 当前交接版本是“代码、黄金证据、标准原文和历史文档”的完整内部快照。文件数
> 会随标准包和交接文档更新变化，应以 `git ls-files | wc -l`（Windows 可用
> `(git ls-files).Count`）和当前 commit 为准。日志和抓包属于历史证据，同一
> 目录中的同类文件不会逐字节重复解释；下面按文件簇、测试编号和用途说明。

## 1. 先看哪一层

| 层级 | 主要目录 | 作用 |
|---|---|---|
| 使用入口 | 根目录 `bootstrap.*`、`run_official_suite.py`、`START-HERE.md` | 同事拉取后如何安装、启动和复跑 |
| 标准用例 | `suites/` | 34 条 TC 的目的、前置条件、官方 TP 骨架、步骤、判据和边界 |
| 标准映射 | `registry/` | 机器可读的 TC 到 3GPP/ETSI 规范、章节和证据映射 |
| 标准原文 | `standards/` | 当前套件已收集的授权原文、版本说明和 SHA256 清单 |
| 执行代码 | `runners/` | 每条 TC 的检查器、统一 runner、证据复跑和报告生成 |
| 历史证据 | `evidence/` | 真实日志、抓包、模拟器输出和本地自检证据 |
| 生成结果 | `generated/` | 统一 runner 生成并纳入版本控制的报告 |
| 交接文档 | `docs/` | 进度、复核、冻结、汇报、标准和仓库说明 |
| 辅助生成 | `tools/` | 验证架构页面等工具 |
| 本地运行产物 | `outputs/`、`__pycache__/` | 不进入 Git，删除不会影响仓库基线 |

## 2. 根目录文件

| 文件 | 含义 |
|---|---|
| `.git/` | Git 本地版本库，不由仓库内容直接管理，不要手工修改。 |
| `.gitattributes` | 统一文本换行，并把 PDF、DOC、PCAP、TGZ 等标记为二进制。 |
| `.gitignore` | 排除缓存、密钥、临时提取物和本地运行产物；保留经过授权的私有标准包 `standards/official/`。 |
| `.github/workflows/verify.yml` | GitHub Actions。代码推送后在 Linux 和 Windows 上运行统一 runner，并检查生成文件是否稳定。 |
| `README.md` | 仓库总览、范围声明、同事快速开始、报告目录和结果词说明。 |
| `START-HERE.md` | 面向第一次接手同事的中文操作手册，包含 clone、一键复跑、单条 TC、结果解释和边界。 |
| `bootstrap.cmd` | Windows 优先入口，绕过 PowerShell 执行策略后调用 `bootstrap.ps1`。 |
| `bootstrap.ps1` | Windows 启动器。查找或准备 Python 3.10+，默认运行统一 runner，也支持 `--doctor`、`--verify-standards` 和 `--colleague-replay`。 |
| `bootstrap.sh` | Linux/macOS 启动器。功能与 PowerShell 启动器对应，使用 POSIX shell。 |
| `run.ps1` | Windows PowerShell 统一 runner 包装入口，适合已经能直接执行 Python 的环境。 |
| `run_official_suite.py` | 核心一键入口。执行标准包哈希、便携性、构建库、34 条套件、自检、证据复跑、L2 适配和报告生成。 |
| `requirements.txt` | 说明核心 runner 只依赖 Python 标准库；没有必须安装的第三方包。 |
| `verification-architecture.html` | 自包含架构浏览器，展示八个模块、34 条 TC、规范映射、执行流程、脚本、证据和限制。 |

## 3. `.github/`

| 路径 | 含义 |
|---|---|
| `.github/workflows/verify.yml` | 持续集成。每次 push 或 pull request 都在两个操作系统上运行仓库基线，防止路径、换行和生成结果漂移。 |

这个目录不是测试证据，它负责自动检查仓库是否仍然可复现。

## 4. `config/`

| 文件 | 含义 |
|---|---|
| `config/README.md` | 本地配置目录说明。明确禁止提交密码、token、私钥、用户标识和生产网络参数；统一 runner 不要求这里存在配置文件。 |

`config/` 当前是预留目录。正常复跑不需要往里放任何东西。

## 5. `standards/`

`standards/` 是授权标准原文的内部交接包，不是 3GPP 全部规范。

| 文件或目录 | 含义 |
|---|---|
| `standards/README.md` | 当前 45 份原文的版本、用途、缺失依赖、版权边界和软件缺失降级规则。 |
| `standards/official/manifest.json` | 每个标准文件的仓库相对路径、规范名、版本、字节数和 SHA256。 |
| `standards/official/<spec>/` | 按规范号分目录保存的 PDF、DOC 或 DOCX。 |

先校验：

```text
python -X utf8 runners/verify_standards_bundle.py
```

通过结果：

```text
STANDARDS BUNDLE: PASS
FILES: 45
TOTAL BYTES: 144416074
```

如果文件缺失、版本与文件名不一致、字节数变化或 SHA256 不匹配，脚本返回非零；
此时不能把该 checkout 当成固定原文快照。`standards/` 不替代 `registry/`：
前者是原文来源，后者是 TC 到条款、消息和证据的机器可读映射。

## 6. `registry/`

| 文件 | 含义 |
|---|---|
| `registry/official_tp_registry.json` | 权威机器可读注册表。记录每条 TC 的模块、官方规范、章节、来源、证据等级、执行脚本和受限项。 |
| `registry/official_tp_library.json` | 由 `suites/` 和注册表生成的官方 TP 库。包含每条 TC 的步骤、判据、官方边界、消息和证据路径。 |

记忆方式：

- `official_tp_registry.json` 是主数据。
- `official_tp_library.json` 是从主数据生成的可执行索引。
- 如果修改套件或注册表，应运行统一 runner 重建库，不要手工编辑生成结果。

## 8. `runners/`

`runners/` 是可执行判定层。目录中大多数 `tc*.py` 文件不是测试输入，而是读取日志、检查字段、输出 PASS/FAIL/RESTRICTED 的检查器。

### 8.1 统一执行和仓库审计

| 文件 | 含义 |
|---|---|
| `run_official_suite.py` 对应的 `runners/*` 脚本由根入口调用。 |
| `run_official_suite_checks.py` | 检查 34 份套件文档、必需章节、元数据和模板完整性。 |
| `build_official_library.py` | 从套件和注册表生成 `official_tp_library.json`。 |

| `gen_detailed_progress.py` | 生成详细进度总表。 |
| `run_tc_selfchecks.py` | 运行所有 checker 的正控和负控，确认脚本本身可用。 |
| `run_tc_evidence.py` | 用仓库中已提交的历史日志复跑所有本地 TC 证据。 |

## 14. 哪些文件属于“必须保留的接手材料”

必须保留并提交：

- 34 条 `suites/official_tp_suites/TC-*.md`；

- `runners/` 中的执行和判定代码；

- `generated/` 中已经冻结的复跑报告；
- `standards/` 中的授权原文、版本说明和 `manifest.json`；
- `docs/` 中的进度、边界、交接和验收文档；

- `__pycache__/`；
- `outputs/`；
- `runners/outputs/tc011-l1-selfcheck/`；
- 编辑器缓存、临时文件、调试日志。

## 15. 两种验证模式必须分开

### 接手同事复现你的结果

使用：

```text
.\bootstrap.cmd --colleague-replay
```

此时应读取 `evidence/` 中固定的黄金证据，并输出：

```text
COLLEAGUE REPLAY: PASS
OFFICIAL_VERDICT: null
```

### 同事验证自己修改后的代码

应使用新的 DUT 验证入口，并要求：

1. 记录他的代码 commit 和二进制 hash；
2. 从他的构建重新生成日志；
3. 新日志放在独立运行目录；
4. 禁止把 `evidence/` 中的旧日志作为他的新结果；
5. 报告标记 `EVIDENCE_SOURCE: FRESH_DUT`；
6. 本地 PASS 仍不能升级为官方一致性 PASS。

当前仓库已经完整支持第一种模式。第二种模式还需要新增独立的 fresh-DUT 入口和硬性证据隔离规则。
