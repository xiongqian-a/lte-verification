## 3. 结果边界

服务器路径和日志只能说明材料和历史运行在哪里。它们不能自动证明：

- UE 或自研协议栈满足 `36.523-1`、`34.229-1` 或其他官方 TP；
- 当前代码版本与历史日志来自同一个 DUT；
- 0 字节抓包中存在有效报文；
- 开源 eNB、EPC、IMS 或 SIP 客户端可以替代合格 System Simulator；
- 第三方入网、运营商入库或 pjsua 合规；
- 本地 `LOCAL_PASS`、`LIMITED_PASS` 或 `SELFCHECK_PASS` 等于
  `OFFICIAL_PASS`。

历史服务器日志统一视为 `HISTORICAL_SNAPSHOT`。同事若要验证自己修改后的
代码，必须从自己的 DUT commit 重新生成日志，并标为 `FRESH_DUT`。

## 8. 路径之间的逻辑链路

### 8.1 IMS 注册与呼叫

```text
pjsua / ims_client
  -> Kamailio P-CSCF / I-CSCF / S-CSCF
  -> pyHSS / MariaDB / Redis / IMS DNS
  -> FreeSWITCH 或对端媒体
  -> phase5-ns/run-baseline20-*/logs
  -> 仓库 evidence/ 中的必要证据切片
  -> TC checker 和统一 runner
```

这条链路解释 TC-011 至 TC-021、TC-030、TC-032、TC-033 的服务器来源。

### 8.2 LTE / EPC 与 PDN

```text
UE / srsUE / nas_test
  -> srsenb / srsRAN_4G
  -> srsepc 或 Open5GS
  -> phase5-ns 或 tc005-o5g 运行目录
  -> NAS / S1AP / MAC / EPC 抓包和进程日志
  -> TC checker 和统一 runner
```

这条链路解释 TC-001 至 TC-010 的服务器来源。`srsRAN_4G` 是代码和可执行
程序入口，`phase5-ns` 与 `tc005-o5g` 是运行证据入口。

### 8.3 媒体与语音活动

```text
pjsua / FreeSWITCH
  -> SIP/SDP 协商
  -> RTP / WAV / AMR 统计
  -> tc024-* 或 tc025-* 证据目录
  -> 媒体 checker
```

这条链路解释 TC-022 至 TC-025。RTP、WAV 和 AMR 统计必须联合阅读，单独
存在某个文件不能证明媒体符合官方判据。

## 9. 服务器路径使用顺序

接手人按以下顺序查路径，效率最高：

1. 先在本文按 TC 或类别定位逻辑入口。
2. 再到 `registry/server_evidence_index.json` 读取机器可读的路径、大小、
   修改时间和仓库副本。
3. 查看仓库中的 `evidence/` 副本和对应 checker 输出。
4. 只有需要确认某个目录或符号链接是否存在时，才查
   `docs/102a-服务器完整目录清单-20260918.txt`。
5. 需要现场复跑时，在服务器上建立新的运行目录；不要覆盖历史快照。

推荐检索命令：

```sh
rg -n "TC-011|ims_register_test" registry/server_evidence_index.json
rg -n "TC-011|ims_register_test" docs/103-服务器文件路径逻辑总表-20260918.md
rg -n "/home/co1750/phase5-ns/run-baseline20" docs/102a-服务器完整目录清单-20260918.txt
```

## 10. 现场复跑和证据隔离规则

服务器历史目录不能直接充当新 DUT 的证据。现场复跑至少记录：

- DUT commit、二进制 SHA256 和构建时间；
- 测试床 commit、Open5GS/srsRAN/Kamailio/FreeSWITCH 版本；
- 网络命名空间、APN、IMPI、IMPU 和非敏感网络参数；
- 新运行目录的绝对路径和 UTC/本地时间；
- 抓包大小、报文数量和哈希；
- 本次运行对应的 TC、官方章节和运行命令；
- 结果词只能使用现场证据支持的级别。

新运行目录建议采用：

```text
/home/co1750/verification-evidence/<tc-id>-<scenario>-<UTC timestamp>/
```

不得提交：

- 密码、私钥、token、数据库凭据；
- 生产网络配置和真实用户身份数据；
- 与本次 TC 无关的完整大日志；
- 0 字节抓包后仍声称存在有效报文。

## 11. 维护规则

服务器测试床变更后，按以下顺序维护：

1. 更新服务器扫描范围和候选文件数。
2. 更新 `registry/server_evidence_index.json`。
3. 更新本文的类别、路径、重点证据和 TC 反查表。
4. 如有新历史证据，更新 `docs/102-服务器与本机路径总表-20260918.md`。
5. 如目录树变化，重新生成 `docs/102a-服务器完整目录清单-20260918.txt`。
6. 运行 `python -X utf8 run_official_suite.py` 和
   `python -X utf8 runners/verify_portable_install.py --full`。

维护时不要把历史日志复制成新的 `OFFICIAL_PASS`。服务器路径是溯源信息，
不是一致性证书。
